# 運用ルール

このリポジトリ（会社のAI書庫）を、作った後どう育てていくかのルールです。

## 1. 成長の道（個人 → 部署 → 全社共通）

```
members/<個人>/        … 1人で試す。壊れても誰も困らない
      │  同じ試作を3回使って役に立つと分かったら
      ▼
plugins/<部署>/        … 部署の道具として正式に持つ。部署のメンバーが使う
      │  複数の部署で同じ道具が欲しくなったら
      ▼
plugins/common/        … 全社共通の道具。誰でも使う
```

- 個人の試作をすぐに全社共通にしない。**まず部署で使ってみて、問題が出ないか確かめる**
- 昇格させる時は、`skills/<名前>/SKILL.md` の中身を部署の実情に合わせて書き直す
  （個人の癖が強い書き方のまま昇格させない）
- 降格（部署の道具をやめる・個人に戻す）も普通にある。使われなくなった道具は消すか、`_廃止/` に移す

## 2. 枝（ブランチ）と取り込み（プルリクエスト）の流れ

```
main（本体）
 │
 ├─ feature/何かの作業 ──┐
 │                        │  変更ができたら
 │                        ▼
 │                 プルリクエスト（取り込み案）
 │                        │  持ち主が見て、問題なければ
 │◀───────────────────────┘  取り込む（マージ）
```

- **`main`に直接保存しない。** 必ず枝を作ってから作業する
- 取り込み案（プルリクエスト）は、**作った本人以外の誰か**が見てから取り込む
  （自分で作って自分で取り込むと、見落としに気づけない）
- 取り込んだ後の枝は消してよい

## 3. 持ち主は2人以上にする

部署の道具（プラグイン）・リポジトリの管理権限は、**必ず2人以上**が持つようにする。

- 1人しか知らない状態を作らない（その人が休んだ・辞めた時に誰も触れなくなる）
- GitHub組織の「Owner（管理者）」権限も2人以上に付与する
- 部署ごとの持ち主の書き方は `.github/CODEOWNERS` の例を参照

## 4. 辞めた人の外し方

人が辞めた・異動した時に、確実に行うこと（順番にチェック）:

1. GitHub組織から、その人のアカウントを外す（Organization の People から Remove）
2. その人が持っていた接続キー・APIキー（もし発行していたら）を無効化し、新しいキーに入れ替える
3. `members/<その人のフォルダ>/` は消さずに残す（過去の経緯が分かるようにするため）。
   フォルダの先頭に「異動日・退職日」をメモしておく
4. `.github/CODEOWNERS` にその人の名前が残っていたら削除する
5. 二段階認証の解除・社内ツールのログイン停止は、GitHub以外のサービスも含めて別途確認する
   （このリポジトリのルールはGitHubの範囲のみをカバーする）

## 5. CODEOWNERS（持ち主）の考え方

`.github/CODEOWNERS` は、「このフォルダの変更は誰の確認が必要か」をGitHubに教えるファイルです。
書き方の例はファイル内にコメントで入っています。部署を作ったら、その部署のフォルダの行を追加してください。

## 6. 検証ログ（このひな形を作った時の実機確認・2026-11-16）

推測ではなく、実際に動かして確かめた結果だけを書く。確かめていないことは「未確認」と明記する。
検証はClaude Code（バージョン2.1.319）とCodex CLI（バージョン0.167.0）で実施した。

### 6.1 Claude Codeへのインストール（確認済み）

- `claude plugin marketplace add ./company-ai-repo-template` → 成功
  - **注意**: 末尾にスラッシュの無い `.` だけだと `Invalid marketplace source format` で失敗する。
    `./` またはフルパス（絶対パス）で指定すること
- `claude plugin install common@company-ai-repo-template` → 成功
- `claude plugin validate .`（リポジトリ全体）/ `claude plugin validate ./plugins/common` → いずれも
  `Validation passed`（警告なし。author/license/iconを追加した後の状態）
- `claude plugin details common` → スキル2本（`save-to-archive`, `start-from-spec`）が認識されている
- **git clone した新しいフォルダでも同じ手順を再現できた**（空フォルダ・.gitkeepが必要な場所は無かった。
  日本語名のフォルダ・ファイルもcloneで欠落しなかった）

### 6.2 Codexでの読み込み（確認済み・実測）

- `AGENTS.md`: Codexは**設定不要で自動的に読む**。`codex exec` で「毎回守ることの項目数」を聞いたら
  正しく「4」と回答し、「項目のタイトル」を聞いたら4項目を正確に引用した（クローン後の新フォルダでも再現）
- `.agents/skills/<name>/SKILL.md`: 使い捨ての検証用フォルダに置いて確認した結果、**設定不要で自動検出される**。
  スキルの中に埋め込んだ合言葉を `codex exec` が正しく読み上げた。
  **このひな形自体には `.agents/skills/` は同梱していない**（スコープ外のため。全社共通の2スキルは
  `plugins/common/skills/` のみに置き、重複管理を避けた）。将来Codex側にも同じスキルをネイティブに
  持たせたい場合は、同じ内容を `.agents/skills/<name>/SKILL.md` にも複製する運用が可能（実測済み）
- **Codexの `codex plugin marketplace add` は、Claude Codeの `.claude-plugin/marketplace.json` を
  そのまま読める**（実測。事前の想定は「変換が必要」だったが、実際に試した結果は違った）。
  `codex plugin marketplace add ./` → 成功 → `codex plugin add common@company-ai-repo-template` → 成功 →
  `codex exec` で確認したところ `common:start-from-spec` `common:save-to-archive`
  という名前でスキルが2本とも使える状態になっていた。
  - ただし、これが確認できたのは**スキルのみのプラグイン**（hooks・mcpServers・userConfigを使っていない）
    だから成立した可能性がある。それらを使うプラグインまで同じように読めるかは**未確認**
  - なお、OpenAIの開発者ポータルには別に「Claude Codeプラグインを提出する」変換ガイドがあるが、
    これは**公開のApps向けディレクトリへ提出する場合の話**で、今回確認した「ローカルの
    `codex plugin marketplace add`」とは別の仕組みだった（混同しないこと）

### 6.4 後始末について（正直に報告）

検証に使った使い捨てのGitHubリポジトリ3つを、権限不足で**削除できていない**。
`gh`（GitHub操作コマンド）に`delete_repo`権限が無く、権限を足すには対話的なブラウザ認証が必要で、
今回の作業では完了できなかった。削除が必要な場合は、作業を依頼した側への報告（チャットの最終報告）に
具体的なリポジトリ名を記載しているので、そちらを参照して持ち主のアカウントから手動で削除してください
（いずれも非公開・テスト用の空同然の内容。会社名・クライアント名は含まない）。

検証に使ったローカルの作業フォルダ・Claude Code/Codexへの一時的なインストール登録は、検証後にすべて
取り消し・退避済み（`rm -rf`は使わず、一時フォルダへ `mv` で退避した）。
