# 会社のAI書庫 ─ ひな形リポジトリ

このリポジトリ（コードやファイルをまとめて保管する場所。GitHub上の「書庫」）は、
自分の会社専用の「AI書庫」を作るための**ひな形（コピーして使う元になる型）**です。

ここに入っているのは実際の仕事の内容ではなく、**置き場所のルールと、最小限の道具（スキル）と、その見本**だけです。
会社の仕事が増えるたびに、このルールに沿ってフォルダや道具を足していきます。

## 1. 全体の地図

```
company-ai-repo-template/
├── CLAUDE.md / AGENTS.md     … AI（Claude Code / Codex）が毎回読む「守ること」と「置き場所の3段」。中身は同じ
├── DESIGN.md                 … 会社のデザインの決まり（色・書体・言葉づかい）の空の型。デザインに関わるものを作る時にAIが読む
├── README.md                 … このファイル（人が読む使い方）
├── .claude-plugin/
│   └── marketplace.json      … このリポジトリに入っている「道具一式（プラグイン）」の目録
├── plugins/
│   ├── common/                … 全社共通の道具（仕様書から始める・書庫に保存する・広報物を作る）
│   ├── sho-san/               … 見本の道具（「SHO-SAN ではこう使っている」。計画を詰める・引き継ぐ・日本語を整える・AI の作業環境を作り直す）
│   └── _部署のひな形/          … 部署用の道具を作るときに複製する型
├── members/
│   └── _ひな形/                … メンバーの名札（個人の書庫の場所・見せたい試作）を作るときに複製する型
├── projects/
│   └── _ひな形/docs/           … 新しい仕事（プロジェクト）を始めるときに複製する、4つの仕様書の空の型
├── templates/
│   ├── settings.json          … Claude Code の安全設定（秘密ファイルを読ませない等）
│   ├── codex-config.md        … Codexに同じ守りをかける方法の説明
│   └── 個人の書庫/             … 本人専用の非公開の書庫（個人の書庫）を作るときの中身の型
├── docs/
│   └── 運用ルール.md           … 育て方のルール（個人→部署→全社共通への「卒業」の流れ）
└── .github/
    └── CODEOWNERS              … 部署ごとの「持ち主」の書き方の例
```

**用語**: 「プラグイン」はAIに新しい道具（スキルやエージェント）を追加で持たせる仕組みのことです。
「スキル」は「こういう時はこの手順で」とAIに教えておく手順書のことです。

## 2. 自分の会社のAI書庫を作る（社長・管理者がやること）

1. GitHub（コードを保管するWebサービス）に、自分の会社の組織（Organization）を作る。非公開（Private）にする
2. このひな形リポジトリを、自分の組織にコピーする（やり方は後述の「頼む文」を使うのが簡単）
   - **組織名・リポジトリ名（GitHub上の名前）は半角英数字で付ける**。日本語を入れると文字が削られて
     意図しない名前になることを実機で確認済み（例: `組織名` という文字をそのまま入れたら、
     その部分が無言で消えて別の名前になった）。フォルダの中の表示名（`members/` 配下など）は
     日本語で問題ない
3. できたリポジトリの `plugins/common/.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の
   `owner`（持ち主）の名前を、自社の名前に変更する
4. 部署ができたら `plugins/_部署のひな形/` を `plugins/<部署名>/` としてコピーし、
   `marketplace.json` にその部署の行を追加する（書き方は `docs/運用ルール.md` を参照）
5. メンバーの個人の書庫と名札（`members/<呼び名>/`）は、各メンバーが最初にAIを使った時に、AIが提案して作る
   （下の「置き場所の3段」を参照。手で作る場合は `members/_ひな形/` と `templates/個人の書庫/` をコピーする）
6. `DESIGN.md` の【　】を埋める（会社の色・書体・言葉づかい）。AIに「DESIGN.md を1問ずつ聞いて埋めて」と頼めば、
   聞き役になって埋めてくれる

## 3. Claude Code で使う（インストール）

このリポジトリを手元に取ってきたら（git clone。「取ってくる」の意味は後述）、ターミナルで次を実行します。

```bash
# 1. この書庫を「道具の目録（マーケットプレース）」として登録する
claude plugin marketplace add ./company-ai-repo-template

# 2. 全社共通の道具（common）をインストールする
claude plugin install common@company-ai-repo-template

# （任意）見本の道具（sho-san）もインストールする
claude plugin install sho-san@company-ai-repo-template

# 3. インストールされたか確認する
claude plugin list
```

Claude Codeのセッション内であれば、`/plugin marketplace add ./company-ai-repo-template` と
`/plugin install common@company-ai-repo-template` でも同じことができます。

インストールが終わると、Claude Codeの中で次のスキルが使えるようになります。

| スキルの呼び方（コマンド） | やること |
|---|---|
| `/common:start-from-spec` | 新しい仕事の「4つの仕様書」を、聞き役になって一緒に埋める |
| `/common:save-to-archive` | 変更をコミット・ブランチ・プルリクエストまで案内する（本体に直接保存しない） |
| `/common:koho-sakusei` | 会社のデザインの決まり（`DESIGN.md`）どおりに広報物を作る |
| `/sho-san:grill` | 計画・設計・決めごとを、共通理解に達するまで1問ずつ詰める（推奨つき） |
| `/sho-san:handoff` | 作業の区切りで README に引き継ぎを残し、次の会話に貼れる「再開の文」を出す |
| `/sho-san:nihongo` | 人に出す日本語（メール・お知らせ・資料など）を自然に整える |
| `/sho-san:org-rebuild` | AI の作業環境（ハーネス）を点検し、1問ずつ決めながら作り直す。研修向けの30分版（点検 → グリル → 決定ログ）もある |

`sho-san` は「SHO-SAN ではこう使っている」の見本です。出典とライセンスは `plugins/sho-san/README.md` を参照してください。
使わない場合は、`marketplace.json` の `sho-san` の行とフォルダを消してかまいません。

該当する言葉を言うだけ（例:「新しい仕事を始めたい」「書庫に保存して」）でも、AIが判断して起動します。

## 4. 置き場所の3段 ─ 会社・プロジェクト・個人

作ったものは、次の3段のどこかに置きます。AIへの決まりとして `CLAUDE.md` / `AGENTS.md` にも同じことを書いてあるので、
人が覚えておかなくても、置き場所は散らかりません。

| 段 | 置き場所 | 何を置くか |
|---|---|---|
| 会社 | この書庫の `plugins/`（`common`・各部署）と `DESIGN.md` | 全員に同じものを配る道具・決まり。直せば全員に届く（例: 広報物のトンマナ、毎回守る決まり） |
| プロジェクト | その仕事の書庫（この書庫なら `projects/<名前>/`） | その仕事で作業する時だけ効く図面・道具・決まり |
| 個人 | 本人専用の非公開の書庫（個人の書庫） | 自分だけのスキル・メモ・好み・試作。育ったら会社の `plugins/` へ上げる |

**個人の書庫は、AIが作ることを提案します。** メンバーがこの書庫で初めてAI（Claude Code・Codex）に作業を頼むと、
AIは `members/` に本人の名札があるかを確かめ、無ければ「あなた専用の非公開の書庫を作りましょうか」と1回だけ聞きます。
同意すると、AIが次をやります（同意しなければ何も作りません）。

1. 会社の GitHub 組織の下に、非公開の書庫 `<呼び名>-ai` を作る（`templates/個人の書庫/` の中身を入れる）
2. この書庫に名札 `members/<呼び名>/README.md` を足す（枝を作り、プルリクエストで取り込む）
3. 自分のスキルを使えるようにする手順を見せる（`claude plugin install me@my-ai` など）

以後、本人だけのスキル・メモは個人の書庫に入り、会社の書庫には混ざりません。

## 5. デザインの決まり（DESIGN.md）

書庫の一番上の `DESIGN.md` は、会社から出るものの色・書体・余白・ロゴ・言葉づかいの決まりです。
AIは、広報物・資料・スライド・画面の見た目や文言を作る前に必ずこれを読みます（`CLAUDE.md` / `AGENTS.md` に書いてある）。
最初は【　】の空欄だけなので、AIに「DESIGN.md を1問ずつ聞いて埋めて」と頼んで埋め、プルリクエストで取り込んでください。
`/common:koho-sakusei` も `DESIGN.md` を先に読みます。

## 6. Codex で使う

Codex（OpenAIのAIコーディングツール）は `AGENTS.md` を読みます。内容は `CLAUDE.md` と同じものです。
Codex独自の「プラグインの目録」の仕組み（`codex plugin marketplace add ./`）は、スキルだけのプラグインなら
Claude Codeの目録ファイルをそのまま読めることを確かめています。フック・MCPを使うプラグインは未確認です
（`docs/運用ルール.md` の「検証ログ」を参照）。
Codexでの安全設定のかけ方は `templates/codex-config.md` を参照してください。

## 7. 安全のための設定（最初からかけておくもの）

`templates/settings.json` を、自分の書庫の `.claude/settings.json` としてコピーして使います。
次を防ぐための最低限の設定です。

- `.env`・鍵ファイル（`*.key` `*.pem` など）・認証情報ファイルをAIに読ませない
- `rm -rf`（全部まとめて消す、取り消せない削除コマンド）を実行させない
- `git push --force`（書庫の履歴を書き換える、取り消せない操作）を実行させない
- `curl` `wget`（外部に向けてデータを送ることもできるコマンド）を無断で実行させない

**この設定は「うっかり」を防ぐガードレールです。悪意を持って回避しようとする行為までは防げません**
（技術的な限界は `templates/codex-config.md` にも記載）。本当に機密性が高いデータを扱う場合は、
別途アカウント管理・権限管理（誰が何を見てよいかの一覧）も必ず行ってください。

## 8. 新しい仕事を始める時の手順（仕様書駆動）

後から機能を足すと、作りが歪みます（「違法建築」と同じ）。だから**先に図面（仕様）を描く**手順にしています。

1. `projects/_ひな形/docs/` を `projects/<仕事の名前>/docs/` としてコピーする
2. `/common:start-from-spec` を呼んで、聞き役のAIと一緒に4つの仕様書を埋める
   - `01-要件.md`: 誰が何を見て、何を決めるか／誰が見てよいか
   - `02-画面.md`: 画面の絵（間取り図）
   - `03-データ.md`: データの出どころと、接続キーの置き場所（書庫には入れない）
   - `04-完成条件.md`: 何ができたら完成か（守りの条件を含む）
3. 仕様書ができたら、小さく作る→確かめる、を繰り返す
4. 変更は `/common:save-to-archive` で、コミット→ブランチ→プルリクエストの手順に乗せる
   （本体＝`main`に直接保存しない）
