# 会社のAI書庫 ─ ひな形リポジトリ

このリポジトリ（コードやファイルをまとめて保管する場所。GitHub上の「書庫」）は、
会社の「AI書庫」を作るための**ひな形（コピーして使う元になる型）**です。

**AI の作業の主役は、一人ひとりの個人のハーネス**（いつも AI を開いている作業フォルダと、その中の指示・スキル・設定）です。
会社の書庫は、それを置き換えるものではありません。**個人のハーネスで育ったもののうち、「みんなにも使ってほしい」と思ったもの**
（スキル・毎回守る決まり・デザインの決まり・仕事の図面など）を、**希望すれば持ち寄って置ける共有の棚**です。

- 使う・使わないは自由です。会社の書庫を使わなくても、個人のハーネスだけで仕事は進められます
- 持ち寄ったものは、ほかのメンバーが次に書庫を開いた時に見られます。会社で有効にした道具は、そのまま使えます
- ここに入っているのは実際の仕事の内容ではなく、**置き場所のルールと、最小限の道具（スキル）と、その見本**だけです

## この書庫でやること3つ

いつもの作業フォルダを Codex または Claude Code で開き、表の文を貼ってください。【この書庫の GitHub の URL】は、自分たちが使っている会社の書庫の URL に置き換えます。ほかの【 】も自分の内容に書き換えます。非公開の書庫は、招待された GitHub アカウントで開きます。

| やること | Codex に貼る文 | Claude Code に貼る文 |
|---|---|---|
| 載せる | 【この書庫の GitHub の URL】の AGENTS.md を読んで、今の Codex の作業フォルダにある【スキル・デザインの見本・図面などの名前かパス】を会社の書庫に載せたい。共有用の呼び名は【自分の呼び名】。置き場所を提案して、枝を作りプルリクエストまで進めて。 | 【この書庫の GitHub の URL】の CLAUDE.md を読んで、今の Claude Code の作業フォルダにある【スキル・デザインの見本・図面などの名前かパス】を会社の書庫に載せたい。共有用の呼び名は【自分の呼び名】。置き場所を提案して、枝を作りプルリクエストまで進めて。 |
| 取り込む | 【この書庫の GitHub の URL】の AGENTS.md を読んで、【持ち主の呼び名かプラグイン名】の【スキル名】を今の作業フォルダの Codex に取り込んで。 | 【この書庫の GitHub の URL】の CLAUDE.md を読んで、【持ち主の呼び名かプラグイン名】の【スキル名】を今の作業フォルダの Claude Code に取り込んで。 |
| 一覧を見る | 【この書庫の GitHub の URL】の CATALOG.md を読んで、スキル名・持ち主・何に使うかを教えて。 | 【この書庫の GitHub の URL】の CATALOG.md を読んで、スキル名・持ち主・何に使うかを教えて。 |

[スキル一覧](CATALOG.md)から、メンバーがおすすめするスキルと、会社のプラグイン（道具のまとまり）に入っているスキルを探せます。[メンバーの棚の見本](members/見本/)には、紹介の書き方と使ってみられるスキルがあります。会社のデザインの決まりは [DESIGN.md](DESIGN.md)、仕事ごとの図面は [projects/](projects/) を見てください。

すでにこのひな形から会社の書庫を作った人は、[ひな形の更新を取り込む](docs/ひな形の更新を取り込む.md)の文を使えます。

### 個人のハーネスから持ち寄る（希望する時だけ）

自分のハーネスで使っているスキルや決まりを会社の書庫に入れたい時は、この書庫のフォルダで AI にこう頼みます。

```
私の個人のハーネス（<自分の作業フォルダ>）にある <スキルや決まりの名前> を、この会社の書庫にも入れたい。
社名・人名・鍵が入っていないか確かめてから、共有の棚・会社の道具・仕事の書庫のどこが合うか提案して、
枝を作ってプルリクエストまで進めて。本体には直接入れないで。
```

元は個人のハーネスに残ります（写して持ち寄るだけです）。取り込むかどうかは、プルリクエストを見て決めます。

## 0. 最初にやること（会社の書庫を使う人）

会社の書庫は、GitHub に1つだけ置きます。持ち寄ったものを使いたい人・持ち寄りたい人が、自分のパソコンに取ってきて（クローン）使います。
**書庫を開くたびに、AIが GitHub から最新を取ってきて、会社の道具（`plugins/`）もそのまま使える**ようにしてあります。
だれかが決まりや道具を直して取り込めば、次に開いた時に全員の手元へ届きます。

### 0-1. 書庫を自分のパソコンに取ってくる（1回だけ）

ターミナル（文字で命令を打つ画面）で、次を実行します。`<組織名>/<書庫の名前>` は管理者から聞いてください。

```bash
gh auth login                              # GitHub にログイン（まだなら。画面の案内に従う）
gh repo clone <組織名>/<書庫の名前>          # 書庫を取ってくる（git clone と同じ）
cd <書庫の名前>                              # 取ってきたフォルダに入る
```

### 0-2. そのフォルダで AI を開く

**必ず、取ってきた書庫のフォルダの中で** AI を起動します（別の場所で開くと、書庫の決まりも道具も効きません）。

```bash
claude      # Claude Code の場合
codex       # Codex の場合
```

初めて開いた時だけ、確認が出ます。

| AI | 出る確認 | 答え方 |
|---|---|---|
| Claude Code | 「このフォルダを信頼しますか（Do you trust the files in this folder?）」 | 「信頼する（Yes）」を選ぶ。これで、開くたびに最新を取ってくる仕組みと、会社の道具（`common`）が有効になる |
| Codex | 「このフォルダを信頼しますか」と、続けて「Hooks need review（自動で動く命令の確認）」 | フォルダを信頼したあと、`1. Review hooks` で中身が `scripts/pull-latest.sh` を動かすだけであることを確かめ、信頼する（`2. Trust all and continue` でも同じ）。中身が変わった時は、また確認が出る |

**Claude Code は、初めて開いた時は一度閉じて（`/exit`）開き直してください。** 1回目の起動で書庫が「道具の目録」として登録され、
2回目の起動から会社の道具（`/common:...`）が使えるようになります（2026-11-18 に実機で確認）。

### 0-3. 連動しているかを確かめる

開いたら、次の3つを確かめます。

1. **最新を取ってきたかの一言が出る**: 開いた直後に、`【書庫の同期】最新を取ってきました` か `【書庫の同期】この書庫は最新です` の一言が出る
   （Claude Code は画面に表示。Codex は AI が最初の返事で伝える）。出ない時は、AI に「書庫の最新を取ってきて」と頼む
2. **書庫の決まりを読んでいる**: AI に「この書庫の決まりを3行で教えて」と聞く。
   「秘密を入れない・本番を触らない・作る前に仕様書・分からなければ聞く」の趣旨が返ってくれば、`CLAUDE.md` / `AGENTS.md` が効いている
3. **会社の道具が見える**（Claude Code）: `/common` と打つと `/common:save-to-archive` などの候補が出る。
   または `/plugin` を開き、`common@company-ai-repo-template` が入っていることを確かめる

### 0-4. 「最新を取ってくる」一言の意味

書庫を開くたびに、`scripts/pull-latest.sh` が静かに動きます。**危ない操作（手元の変更を消す・履歴を書き換える）は一切しません。**
早送りで取り込める時だけ取り込み、それ以外は何も変えずに一言だけ出します。

| 出る一言 | 意味と、やること |
|---|---|
| 最新を取ってきました | GitHub の更新を取り込んだ。そのまま作業してよい。「会社の道具も新しくなりました」と出たら、Claude Code では `/reload-plugins` を実行 |
| この書庫は最新です | 何もしなくてよい |
| 手元に保存（コミット）していない変更があるため、見送りました | 自分の作業が残っている。AI に「書庫に保存して」と頼んでから開き直す |
| 手元と GitHub の記録が分かれているため、自動では取り込みませんでした | 自分の保存と他の人の更新がすれ違っている。AI に「安全な直し方を教えて」と相談する（自分で消したりしない） |
| GitHub につながらず、確かめられませんでした | インターネットか GitHub のログイン（`gh auth status`）を確かめる。手元の内容のままなら作業はできる |
| 枝「…」はまだ GitHub とつながっていない | 自分で作った作業用の枝（ブランチ）にいる。問題なし |

手で動かすこともできます: `bash scripts/pull-latest.sh --text`

## 1. 全体の地図

```
company-ai-repo-template/
├── CLAUDE.md / AGENTS.md     … AI（Claude Code / Codex）が毎回読む「守ること」と「置き場所の3段」。中身は同じ
├── DESIGN.md                 … 会社のデザインの決まり（色・書体・言葉づかい）の空の型。デザインに関わるものを作る時にAIが読む
├── README.md                 … このファイル（人が読む使い方）
├── CATALOG.md                … メンバーと会社のプラグインのスキル一覧
├── .claude-plugin/
│   └── marketplace.json      … このリポジトリに入っている「道具一式（プラグイン）」の目録
├── .claude/
│   └── settings.json         … Claude Code で開いた時の設定（SHO-SAN おすすめの守り・最新を取ってくる・会社の道具を有効にする）
├── .codex/
│   ├── config.toml           … Codex のおすすめの設定（書けるのは書庫の中だけ・外に出る前に確かめる）
│   ├── rules/default.rules   … Codex で止めるコマンド・確かめるコマンドの一覧
│   └── hooks.json            … Codex で開いた時に最新を取ってくる・危ない操作を止める見張り番を呼ぶ設定
├── scripts/
│   ├── pull-latest.sh        … 書庫を開いた時に GitHub から最新を取ってくる小さな仕組み（危ない操作はしない）
│   ├── guardrail.py          … 危ない操作を動く直前に止める見張り番（Claude Code・Codex 共通。止める理由を日本語で出す）
│   └── catalog.py            … スキル一覧を作る
├── plugins/
│   ├── common/                … 全社共通の道具（書庫に保存する・広報物を作る）
│   ├── sho-san/               … 見本の道具13本（「SHO-SAN ではこう使っている」。仕事の進め方・資料作成・画面づくり）
│   ├── ai-dev-steps/          … 開発の手順 1〜9 を1段1スキルで進める道具（入口は dev-start）
│   └── _部署のひな形/          … 部署用の道具を作るときに複製する型
├── members/
│   ├── _ひな形/                … メンバーの名札とおすすめの棚を作るときに複製する型
│   └── 見本/                   … 棚の紹介とスキルの見本
├── projects/
│   └── README.md               … 仕事ごとのフォルダの置き方（作り方は ai-dev-steps に従う）
├── templates/
│   ├── settings.json          … Claude Code の安全設定（秘密ファイルを読ませない等）
│   ├── codex-config.md        … Codexに同じ守りをかける方法の説明
│   └── 個人の書庫/             … 本人専用の非公開の書庫（個人の書庫）を作るときの中身の型
├── docs/
│   ├── おすすめの設定.md        … 上の設定を1行ずつ「何を止めるか・なぜか・外したい時」で説明したもの
│   ├── 運用ルール.md           … 育て方のルール（個人→部署→全社共通への「卒業」の流れ）
│   └── ひな形の更新を取り込む.md … 既存の書庫に今回の更新を足すための文
└── .github/
    ├── CODEOWNERS              … 部署ごとの「持ち主」の書き方の例
    └── workflows/catalog.yml  … main のスキル一覧を自動更新する
```

**用語**: 「プラグイン」はAIに新しい道具（スキルやエージェント）を追加で持たせる仕組みのことです。
「スキル」は「こういう時はこの手順で」とAIに教えておく手順書のことです。

## 2. 自分の会社のAI書庫を作る（社長・管理者がやること）

1. GitHub（コードを保管するWebサービス）に、自分の会社の組織（Organization）を作る。非公開（Private）にする
2. このひな形リポジトリを、自分の組織にコピーする（やり方は後述の「頼む文」を使うのが簡単）
   - **組織名・リポジトリ名（GitHub上の名前）は半角英数字で付ける**。日本語を入れると文字が削られて
     意図しない名前になることを実機で確認済み（例: `組織名` という文字をそのまま入れたら、
     その部分が無言で消えて別の名前になった）。フォルダの中の表示名（`members/` 配下など）は
     日本語で問題ない
3. できたリポジトリの `plugins/common/.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の
   `owner`（持ち主）の名前を、自社の名前に変更する
4. 部署ができたら `plugins/_部署のひな形/` を `plugins/<部署名>/` としてコピーし、
   `marketplace.json` にその部署の行を追加する（書き方は `docs/運用ルール.md` を参照）
5. メンバーの個人の書庫と名札（`members/<呼び名>/`）は、各メンバーが最初にAIを使った時に、AIが提案して作る
   （下の「置き場所の3段」を参照。手で作る場合は `members/_ひな形/` と `templates/個人の書庫/` をコピーする）
6. `DESIGN.md` の【　】を埋める（会社の色・書体・言葉づかい）。AIに「DESIGN.md を1問ずつ聞いて埋めて」と頼めば、
   聞き役になって埋めてくれる
7. メンバーに、書庫の場所（`<組織名>/<書庫の名前>`）と、上の「0. 最初にやること」を伝える。
   メンバーを GitHub の組織に招待し、書庫を読める・書ける権限を付ける
8. （推奨）`main` に「レビュー必須」の保護ルールを掛ける（GitHub の Settings → Branches）。
   全員の手元に自動で届く書庫なので、取り込む前に必ず1人が確かめる形にしておく

**目録の名前を変える時の注意**: `.claude-plugin/marketplace.json` の `"name"`（最初は `company-ai-repo-template`）を
自社の名前に変えた場合は、`.claude/settings.json` の `extraKnownMarketplaces` の名前と、
`enabledPlugins` の `@` の後ろも、同じ名前に揃えてください（揃っていないと、会社の道具が届きません）。

## 3. Claude Code で使う（会社の道具が届く仕組み）

**手でインストールしなくても、書庫のフォルダで Claude Code を開けば、会社共通の道具（`common`）が使えます。**
`.claude/settings.json` に次の2つを書いてあるからです（Claude Code の公式の仕組み。`extraKnownMarketplaces` と `enabledPlugins`）。

```json
"extraKnownMarketplaces": {
  "company-ai-repo-template": { "source": { "source": "directory", "path": "./" } }
},
"enabledPlugins": {
  "common@company-ai-repo-template": true
}
```

- `extraKnownMarketplaces`: 「この書庫そのものを、道具の目録（マーケットプレース）として使う」という指定。
  `"path": "./"` は書庫の一番上を指す（取ってきた場所がどこでも、各自の書庫のフォルダに読み替わる。実機で確認）
- `enabledPlugins`: 「その目録のうち `common` を、この書庫では全員オンにする」という指定
- フォルダを「信頼する」と答えた後にだけ効きます（信頼していないフォルダでは、Claude Code はこの指定を無視します）

**道具の更新は、書庫の更新と同じです。** 道具は書庫のフォルダから直接読み込まれるので、開いた時に最新を取ってくれば
（0-4 の仕組み）、道具も最新になります。会話の途中で取り込んだ時は `/reload-plugins` で今の会話にも反映されます。
このため、この使い方では「自動更新」の設定は要りません。

**部署の道具や見本（`sho-san`）も、全員にオンにしたい時**は、`enabledPlugins` に行を足して、プルリクエストで取り込みます。

```json
"enabledPlugins": {
  "common@company-ai-repo-template": true,
  "sho-san@company-ai-repo-template": true
}
```

個人で足したい時は、Claude Code の中で `/plugin install sho-san@company-ai-repo-template` を実行します。

### 書庫の外（ほかのフォルダ）でも会社の道具を使いたい時

書庫以外のフォルダで作業する時にも会社の道具を使いたい人は、GitHub の書庫を目録として自分のパソコンに登録します。
この場合は GitHub から写しを取ってくる方式になるので、**自動更新をオンにします**（社外の目録は、最初は自動更新がオフです）。

```bash
claude plugin marketplace add <組織名>/<書庫の名前>                 # GitHub の書庫を目録として登録
claude plugin install common@company-ai-repo-template --scope user  # 自分のパソコン全体で使う
```

自動更新のオンは、次のどちらかで行います（Claude Code 公式の方法）。

- Claude Code の中で `/plugin` を開き、**Marketplaces** の画面で `company-ai-repo-template` を選び、**Enable auto-update** を選ぶ
- または、自分の設定ファイル（`~/.claude/settings.json`）の目録の指定に `"autoUpdate": true` を書く

```json
"extraKnownMarketplaces": {
  "company-ai-repo-template": {
    "source": { "source": "github", "repo": "<組織名>/<書庫の名前>" },
    "autoUpdate": true
  }
}
```

自動更新は、起動してから少し後（最大10分ほど）に裏で行われ、「Plugin updated … Run /reload-plugins to apply」と出たら反映できます。
`DISABLE_AUTOUPDATER=1` などで Claude Code の自動更新を止めているパソコンでは、`FORCE_AUTOUPDATE_PLUGINS=1` も合わせて設定しないと動きません。
手で更新する時は `claude plugin marketplace update company-ai-repo-template` を実行します。

書庫で開いた時（または上のインストールの後）、Claude Codeの中で次のスキルが使えるようになります（`sho-san` は、オンにした場合だけ）。

| スキルの呼び方（コマンド） | やること |
|---|---|
| `/common:save-to-archive` | 変更をコミット・ブランチ・プルリクエストまで案内する（本体に直接保存しない） |
| `/common:koho-sakusei` | 会社のデザインの決まり（`DESIGN.md`）どおりに広報物を作る |
| `/sho-san:grill` | 計画・設計・決めごとを、共通理解に達するまで1問ずつ詰める（推奨つき） |
| `/sho-san:handoff` | 作業の区切りで README に引き継ぎを残し、次の会話に貼れる「再開の文」を出す |
| `/sho-san:nihongo` | 人に出す日本語（メール・お知らせ・資料など）を自然に整える |
| `/sho-san:org-rebuild` | AI の作業環境（ハーネス）を点検し、1問ずつ決めながら作り直す。研修向けの30分版（点検 → グリル → 決定ログ）もある |
| `/ai-dev-steps:dev-start` | 道具やサービスを作る時の「開発の手順 1〜9」で、今どの段か・次に何をするかを教える（各段は `dev-concept`〜`dev-attack`。社内の道具なら 5 価値の検証・7 価格は飛ばす） |

`sho-san` は「SHO-SAN ではこう使っている」の見本です。出典とライセンスは `plugins/sho-san/README.md` を参照してください。
`ai-dev-steps` は開発の手順 1〜9 の道具です（出典は `plugins/ai-dev-steps/NOTICE.md`）。Codex では `$ai-dev-steps:dev-start` で呼びます。
使わない場合は、`marketplace.json` の `sho-san`・`ai-dev-steps` の行とフォルダを消してかまいません。

該当する言葉を言うだけ（例:「新しい仕事を始めたい」「書庫に保存して」）でも、AIが判断して起動します。

## 4. 置き場所の3段 ─ 会社・プロジェクト・個人

作ったものは、まず個人（自分のハーネス）に置きます。みんなに配りたくなったら、希望して会社やプロジェクトの段に持ち寄ります。AIへの決まりとして `CLAUDE.md` / `AGENTS.md` にも同じことを書いてあるので、
人が覚えておかなくても、置き場所は散らかりません。

| 段 | 置き場所 | 何を置くか |
|---|---|---|
| 会社 | この書庫の `members/<呼び名>/`、`plugins/`（`common`・各部署）、`DESIGN.md` | メンバーがおすすめするもの、会社から配る道具、デザインの決まり |
| プロジェクト | その仕事の書庫（この書庫なら `projects/<名前>/`） | その仕事で作業する時だけ効く図面・道具・決まり |
| 個人 | 自分のハーネス（いつもの作業フォルダ。GitHub に上げるなら本人専用の非公開の書庫） | 自分のスキル・メモ・好み・試作。ここが基本。共有したいものは、自分の棚など会社の書庫へ持ち寄れる |

**個人の書庫は、AIが作ることを提案します。** メンバーがこの書庫で初めてAI（Claude Code・Codex）に作業を頼むと、
AIは `members/` に本人の名札があるかを確かめ、無ければ「あなた専用の非公開の書庫を作りましょうか」と1回だけ聞きます。
同意すると、AIが次をやります（同意しなければ何も作りません）。

1. 会社の GitHub 組織の下に、非公開の書庫 `<呼び名>-ai` を作る（`templates/個人の書庫/` の中身を入れる）
2. この書庫に名札 `members/<呼び名>/README.md` を足す（枝を作り、プルリクエストで取り込む）
3. 自分のスキルを使えるようにする手順を見せる（`claude plugin install me@my-ai` など）

以後、本人だけのスキル・メモは個人の書庫に入り、会社の書庫には混ざりません。

## 5. デザインの決まり（DESIGN.md）

書庫の一番上の `DESIGN.md` は、会社から出るものの色・書体・余白・ロゴ・言葉づかいの決まりです。
AIは、広報物・資料・スライド・画面の見た目や文言を作る前に必ずこれを読みます（`CLAUDE.md` / `AGENTS.md` に書いてある）。
最初は【　】の空欄だけなので、AIに「DESIGN.md を1問ずつ聞いて埋めて」と頼んで埋め、プルリクエストで取り込んでください。
`/common:koho-sakusei` も `DESIGN.md` を先に読みます。

## 6. Codex で使う

Codex（OpenAIのAIコーディングツール）は `AGENTS.md` を読みます。内容は `CLAUDE.md` と同じものです。

**開いた時に最新を取ってくる仕組み**は、Codex の公式のフック（`.codex/hooks.json` の `SessionStart`）で、
Claude Code と同じ `scripts/pull-latest.sh` を動かしています。Codex では、次の2つの確認を通った後にだけ動きます。

1. そのフォルダを「信頼する」と答える（信頼していないフォルダでは `.codex/` の設定は読まれない）
2. 起動時に出る「Hooks need review」で、フックの中身を確かめて信頼する（`/hooks` からも確かめられる）。
   `.codex/hooks.json` を書き換えると、もう一度確認が出る

信頼しなかった場合でも、`AGENTS.md` に「作業の前に `bash scripts/pull-latest.sh --text` を実行する」と書いてあるので、
AI が作業の前に最新を取ってきます。
Codex独自の「プラグインの目録」の仕組み（`codex plugin marketplace add ./`）は、スキルだけのプラグインなら
Claude Codeの目録ファイルをそのまま読めることを確かめています。フック・MCPを使うプラグインは未確認です
（`docs/運用ルール.md` の「検証ログ」を参照）。
Codexでの安全設定は、この書庫の `.codex/config.toml`・`.codex/rules/default.rules`・`.codex/hooks.json` に入っています（説明は `docs/おすすめの設定.md`）。

## 7. 安全のための設定（SHO-SAN おすすめの設定）

この書庫には、SHO-SAN が実際に使っている守りを、どの会社でも使える形に直した設定が最初から入っています。
**1行ずつ「何を止めるか・なぜか・外したい時」は [`docs/おすすめの設定.md`](docs/おすすめの設定.md) にまとめてあります。**

- **毎回確かめる**: ファイルの書き換え・コマンドの前に「よいですか」と聞く（慣れたら自分の設定で `acceptEdits` に）
- **「何も聞かずに全部やる」モードは使えなくしてある**（公式も、隔離した環境の中だけで使うこととしている）
- **止める**: `.env`・鍵・パスワードのファイルを読む／ホームフォルダやシステムを丸ごと消す／`sudo`／強制 push／`curl` `wget` などの送信コマンド
- **確かめる**: `git push`／フォルダごと消す／GitHub の上での投稿・取り込み／本番への反映・公開／メッセージの送信（MCP の道具）／AI が守りの設定を書き換えること
- **見張り番**（`scripts/guardrail.py`）: コマンドが動く直前に中身を見て、つないだ形や書き方を変えた形でも危ないものを止め、理由を日本語で出す
- Codex にも同じ守り（`.codex/config.toml`・`.codex/rules/default.rules`・`.codex/hooks.json`）が入っている

**この設定は「うっかり」を防ぐガードレールです。悪意を持って回避しようとする行為までは防げません。**
本当に機密性が高いデータを扱う場合は、別途アカウント管理・権限管理（誰が何を見てよいかの一覧）も必ず行ってください。
`templates/settings.json` は、同じ「止める・確かめる」だけを別の書庫に入れたい時に使う写しです。

## 8. 新しい仕事を始める時の手順（仕様書駆動）

後から機能を足すと、作りが歪みます（「違法建築」と同じ）。だから**先に図面（仕様）を描く**手順にしています。
手順は開発の手順の道具 `ai-dev-steps` に入っています。

1. AI に「新しい道具を作りたい。dev-start で今どの段か教えて」と頼む（Claude Code は `/ai-dev-steps:dev-start`、Codex は `$ai-dev-steps:dev-start`）
2. 段1で仕事の名前を日本語で付けると、`projects/<仕事の名前>/` ができる。入口の `README.md` に、今の段・進み具合・最近の動きが残っていく
3. あとは AI の質問に1問ずつ答え、できた docs を見て「OK」と言うと次の段へ進む。社内で使う道具なら、5 価値の検証・7 価格は飛ばす
4. 変更は `/common:save-to-archive` で、コミット→ブランチ→プルリクエストの手順に乗せる
   （本体＝`main`に直接保存しない）
