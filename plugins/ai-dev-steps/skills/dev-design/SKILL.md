# dev-design ─ 段8 デザイン（内装・外観）

間取り（画面の並び）が決まって建物が建ったら、内装と外観です。
いきなり色を塗らず、**雰囲気 → 決まり → 画面** の順に進めます。決まり（DESIGN.md）にしておくと、次に作る画面も資料も同じ見た目にそろいます。

## 始める前に

- 書庫の一番上の `DESIGN.md` は**会社全体の決まり**。この段では書き換えない
  - あって【　】が無い → 会社の決まりはもうある。**決まりは変えずに読むだけにして**、画面に当てる所（手順4）から始める
  - あって【　】が残っている、または無い → 会社の決まりは、会社として別に決める（この道具1つのために書き換えない）。この仕事では `projects/<仕事の名前>/docs/デザイン.md` に、この道具だけの決まりを書く（手順1から）。会社の決まりが後でできたら、そちらを優先する
  - この道具だけ会社の決まりと違う見た目にしたい所があれば、`docs/デザイン.md` に「会社の決まりとの違い」として書く（会社の `DESIGN.md` は直さない）
- `docs/00-コンセプト.md`（誰が使うか）と `docs/02-画面.md` を読む

## 進め方

### 1. 雰囲気を言葉で集める

1問ずつ聞く。推奨を添える。

- 使う人に、どう感じてほしいか（例: 落ち着いて信頼できる／親しみやすい／きびきび速い）
- 「この感じに寄せたい」見本と、「こうはしたくない」見本。**寄せたい見本は必ず1つ以上もらう**（自社のサイト・会社の資料やチラシ・寄せたいサービスの画面のスクリーンショット・URL など）。見本が無いまま AI が考えた案で進めない
  - 本人が「特に無い」と言う時は、使う人が毎日見ている画面（社内で使っている道具・よく使うサービス）を2〜3挙げて、「どれに近いと使いやすいですか？」と聞く
  - もらった見本から、色・文字の太さ・余白の取り方・情報の詰め具合を読み取り、`docs/design/見本のメモ.md` に「見本 → 読み取ったこと」の形で残す
- 必ず使う色・ロゴがあるか（会社の色など）

### 2. ムードボードを3方向並べる

`docs/design/ムードボード.html` に、方向の違う3案を1枚に並べる。各案に入れるもの:

- 方向の名前と、ひとことの説明
- 色の見本（メイン・強調・地・文字・線の5色。色の番号つき）
- 文字の見本（見出し・本文・数字。パソコンに最初から入っている書体か、無料で使える書体を推奨）
- その方向で描いた、いちばん大事な画面の小さな見本（`02-画面.md` の下書きに色と文字を当てたもの）
- **どの見本の、どこを参考にしたか**（例: 「自社サイトの紺と余白の広さ」）。参考の無い案は作らない

決まり:
- 1つの HTML ファイルで開ける。外の画像・ライブラリは読み込まない
- 写真やイラストは、本人が「使ってよい」と言ったものだけ使う。無ければ色と文字だけで作る
- 文字と地の色は、読みやすい濃さの差をとる（薄い灰色の地に薄い灰色の文字にしない）
- 共有ページを作れる道具があれば、それで URL にして渡す

### 2.5 本人に選んでもらう（ここで止まる）

「私なら案◯です。理由は〜」と推奨を添えて聞き、**本人が選ぶまで次へ進まない**。組み合わせ（案Aの色＋案Cの一覧）や「どれも違う」も受け付ける。「どれも違う」なら、何が違うかを1問ずつ聞いて、見本を足してから作り直す。

### 3. 決まりを書く

選んだ方向をもとに、`docs/デザイン.md`（会社の `DESIGN.md` が埋まっていない時。上の「始める前に」）の項目を**1問ずつ**埋める（色・文字・余白と並べ方・ロゴと写真・言葉づかい・使わないもの・見本）。
会社の `DESIGN.md` の型がある書庫なら、その見出しをそのまま使う。無ければ次の見出しで作る:

```markdown
# デザインの決まり（<仕事の名前>）
## 1. 目指すこと（印象をひとことで・主な読み手）
## 2. 色（メイン・強調・地・文字・線。それぞれの使い方）
## 3. 文字（和文の書体・英数字の書体・見出しと本文の大きさの比）
## 4. 余白・並べ方
## 5. ロゴ・写真・図
## 6. 言葉づかい
## 7. 使わないもの
## 8. 見本（良い見本・悪い見本。もらった見本と、どこを参考にしたか）
```

強調の色は「1画面に1か所」など、**使いすぎない決まり**も必ず入れる。

### 4. 画面に当てる

- 書いた決まりを本人に見せて OK をもらってから当てる
- 決まりの色・文字を、画面のコードで「1か所で決めて、全体で使う」形にする（色や大きさを画面ごとに書かない）
- 1画面ずつ当て、`02-画面.md` の並びが崩れていないかを確かめる
- 迷う所（ボタンの形・一覧の見せ方など）は、**使い捨ての HTML** に2〜3案並べて選んでもらう。選んだら、その HTML は消してよい（選んだ理由は DESIGN.md か `02-画面.md` に残す）
- 見た目を変えるために画面の並びや機能を変えたくなったら、先に `02-画面.md` を直す

### 5. 点検する

- 新しい AI を起こし（`dev-build` の「別の目の点検」と同じ起こし方）、DESIGN.md と画面を渡して「決まりと違う所」を挙げてもらう
- `design-review`・`visual-design`・`ux-review` スキルや、公式プラグインの `frontend-design` が入っていれば使ってよい（無くても回る）

## 終わりの確かめ

- 決まり（会社の `DESIGN.md` か `docs/デザイン.md`）に【　】が残っていない。会社の `DESIGN.md` を書き換えていない
- 寄せたい見本が1つ以上あり、どこを参考にしたかが書いてある
- **本人が当てた後の画面を見て OK を出した**（直したい所は「直す・図面を変える・後で」に分けて決める）
- 画面に当たっている（色・文字が1か所で決まっている）
- 仕事の `README.md` の進み具合の「8 デザイン」に ○ と日付を入れ、次は `dev-attack`（段9 攻撃して直す）だと伝える

## 共通の決まり（どの段でも）

- **設計を変える時は、先に図面（docs）を直してからコードを直す**
- **直す前に、なぜそうなったか（根本原因）を説明してから直す**
- **分からないことは作らずに聞く**。1問ずつ、AI の推奨を添えて聞く（`grill` スキルが入っていれば使う）
- **鍵（パスワード・API キー・トークン・.env の中身）を docs にもコードにも書かない**。書くのは「どこに置いたか」だけ
- **段の終わりは、本人の OK が出るまで次の段へ進まない**。AI が推奨で決めた所は「（推奨で決めた・本人の確認待ち）」と書き、OK をもらったら外す。方向を変えたいと言われたら、その段か前の段の docs から直す
- **段が進んだ・決めたことがあった時は、仕事の `README.md` を直す**: 進み具合の表と「今の段」を直し、「最近の動き」の一番上に `- 日付: 何をしたか・決めたこと` を1行足す
