# dev-prototype ─ 段4 試作（模型・モデルルーム）

家を建てる前の模型と同じで、**触って確かめるためのもの**です。きれいさや速さは後回しにして、
「この流れで本当に使えるか」が分かるところまでを、手早く作ります。

## 始める前に

- `docs/01-要件.md`・`02-画面.md`・`03-データ.md` を読む。足りなければ、その段のスキル（dev-spec・dev-wireframe）を案内して止まる
- 作り方（使う言語・仕組み）を1つ推奨して、本人に確かめる。迷ったら「1つの HTML ファイル＋ブラウザの中だけにデータを保存」を推奨する（入れる物が少なく、壊れにくい）。複数人で同じデータを見る必要がある時だけ、サーバーのある作りを提案する
- 置き場所: `projects/<仕事の名前>/prototype/`（`projects/` が無い書庫なら `prototype/`）

## 試作の決まり

- **本物の鍵・本番のデータを使わない**。外部サービスにはつながず、架空のデータで代わりをする（例: メールを取る所は、架空のメール10件を読み込むだけにする）
- **自分のパソコンの中だけで動かす**。公開しない
- **1画面ずつ、端から端まで動かす**（薄い縦切り）。全部の画面を半分ずつ作るより、1画面を「入れる→保存→表示」まで通す方が早く確かめられる
- `02-画面.md` に無い画面・ボタンを足さない。足したくなったら、先に `02-画面.md` を直す

## 進め方

1. **試作の完成条件を先に書く**: `docs/04-完成条件.md` の「1. 何ができたら完成か」に、試作で確かめる操作と結果を3〜5行書く（例: 「貸し出す」を押すと、一覧のその備品が「貸出中」になる）。各行に ○× の欄をつける。ファイルが無ければ下の型で作る
2. **1画面目を作る**: いちばん大事な画面から。作ったら自分で開いて、完成条件の行を1つずつ試す
3. **残りの画面を作る**: 1画面ずつ、同じように試す
4. **本人に触ってもらう**: 開き方（どのファイルをどう開くか・どのコマンドで動くか）を3行以内で伝える
5. **気づいたことを分ける**: 本人の感想を「直す（今の図面の範囲）」「図面を変える（docs を先に直す）」「後で（作らないものに入れる）」の3つに分けて見せ、どれにするか確かめる

## `04-完成条件.md` の型（試作の段で作る分）

全社共通の `start-from-spec` と同じ見出しです。2・3 は段6（dev-build）で仕上げます。

```markdown
# 完成条件

> 検査の基準を先に書く。「何ができたら完成か」を具体的な操作と結果のセットで書く。
> 守りの条件（キーがコードに無い・ログイン無しで開けない等）も必ず含める。

## 1. 何ができたら完成か（操作 → 期待する結果）
| # | 操作 | 期待する結果 | 試作 | 本番 |
|---|---|---|---|---|
| 1 | | | ○× | |

## 2. 守りの条件
（段6で書く）

## 3. 誰が確認するか（作った人以外の、確かめる役）
（段6で書く）
```

## 終わりの確かめ

- 完成条件の「試作」の列が全部 ○（× が残るなら、直すか、本人と相談して条件を変える。条件を変えたら docs を先に直す）
- 本人が触った
- `00-コンセプト.md` の進み具合の「4 試作」に ○ と日付と置き場所を入れる
- 次の段を伝える: 売るものなら `dev-validate`（段5 価値の検証）、社内の道具なら `dev-build`（段6 本番の実装）

## 共通の決まり（どの段でも）

- **設計を変える時は、先に図面（docs）を直してからコードを直す**
- **直す前に、なぜそうなったか（根本原因）を説明してから直す**
- **分からないことは作らずに聞く**。1問ずつ、AI の推奨を添えて聞く（`grill` スキルが入っていれば使う）
- **鍵（パスワード・API キー・トークン・.env の中身）を docs にもコードにも書かない**。書くのは「どこに置いたか」だけ
