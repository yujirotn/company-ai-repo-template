# dev-attack ─ 段9 攻撃して直す（防犯の点検）

泥棒の目で自分の家を見ると、鍵のかけ忘れに気づけます。ここでは AI を「攻める側」にして、作った道具の穴を探し、直します。

## 0. 最初に必ず確かめる（ここを飛ばさない）

攻撃は、**自分で作った道具を、自分の練習環境で**だけ行います。他人のもの・本番に試すと、壊したり、法律に触れたりします。
次の4つを本人に1つずつ聞き、**全部「はい」になるまで先へ進まない**。

1. 対象は、自分（自分の会社）で作った道具ですか？（他社のサービス・借りているサービスそのものは対象にしない）
2. 攻撃する先は、自分のパソコンの中（`localhost` など）か、自分専用の練習環境ですか？ 本番（お客様が使っている環境）ではありませんか？
3. 練習環境のデータは、架空のデータか複製ですか？ 壊れても困りませんか？
4. 練習環境が外部のサービス（置き先・データベース・AI の利用など）を使っている時、そのサービスの決まりで、自分の環境を試すことが許されていますか？（分からなければ、外部には送らず、コードを読むだけにする）

どれかが「いいえ」「分からない」なら、**動いているものへの攻撃はしない**。コードと docs を読むだけの点検（手順2の「読む」だけ）に切り替え、そう伝える。

確かめた答えを `docs/reviews/攻撃-<日付>.md` の一番上に書く。

## 1. 攻める範囲を決める

`docs/01-要件.md`（見てよい人・見せてはいけないもの）・`03-データ.md`（つなぐ先・鍵）・`04-完成条件.md`（守りの条件）を読み、
攻める先（練習環境の URL）と、守りたいもの（個人の情報・金額・鍵など）を書き出して本人に確かめる。

## 2. 攻める側の AI を起こす

作った AI とは別の AI を**新しく起こし**、何も先入観のない状態で攻めさせます（`dev-build` の「別の目の点検」と同じ起こし方。Claude Code はサブエージェント、Codex はサブエージェントか新しい `codex exec`、どちらでも新しい会話に貼ってよい）。
渡すもの: 読む場所・攻めてよい先（練習環境の URL だけ）・手順0の答え・下の依頼文。**作った AI の結論は渡さない。**

### 依頼文

```
あなたは、この道具を攻める側の点検役です。目的は穴を見つけて直すことです。
攻めてよい先は <練習環境の URL> だけです。それ以外（本番・外部のサービス・ほかの人の物）には、何も送らないでください。
データを消す・大量に送る・止めるような試し方はしないでください。コードも書き換えないでください。
読む場所: <docs のフォルダ> と <コードのフォルダ>

次の順に、まずコードと docs を読んで当たりを付け、当たりがある所だけを練習環境で試してください。
1. 鍵の漏れ: コード・設定・docs・記録・画面の中に、鍵（API キー・パスワード・トークン）が見えないか
2. 入り口: ログインしないで開ける画面・データの取り口はないか
3. 他人のデータ: URL や送る中身の ID を書き換えると、ほかの人のデータが見えたり変えられたりしないか
4. 入力への仕込み: 入力欄に仕込んだ文字で、画面に別の動きをさせたり、データベースに命令を通したりできないか
5. 外への送り出し: 外に出してはいけないデータ（docs/01-要件.md の「見せてはいけない」）が、外部のサービスや記録に出ていないか
6. AI への仕込み: 道具の中で AI を使っているなら、読み込む文書やメールに仕込んだ指示で、AI に秘密を出させたり、勝手な操作をさせたりできないか
7. 古い部品: 穴が知られている古い部品を使っていないか

見つけたものを、重い順に「重大・高・中・低」で、
・どこ（画面・ファイルと行）
・誰が、どうやって、何を得るか（試した手順。試していないなら「読んだだけ」と書く）
・直し方の案
の形で書いてください。理屈の上の心配と、実際に刺さった穴は分けてください。
```

## 3. 根本原因を説明してから直す

穴が見つかったら、**すぐ直さない**。先に本人へ短く説明する。

1. 何ができてしまうか（誰が何を得るか）
2. なぜそう作ってしまったか（根本原因）
3. どう直すか・同じ原因の穴がほかにないか

直し方が図面に関わる（見てよい人・鍵の置き場所・画面の流れが変わる）なら、先に docs を直す。直すのは見つかった穴だけ。

## 4. もう一度攻める

- 直したら、**また新しい AI を起こして**同じ依頼文で攻めさせる（前の攻め役に「直しました」と言わない）
- 合格: 「重大」と「高」が0件。「中」「低」は記録に残し、本人と直すか決める
- 3回回しても合格しない・指摘が間違いだと思う根拠がある → 止めて、指摘と反論を並べて本人に判断してもらう

## 5. 記録する

`docs/reviews/攻撃-<日付>.md` に残す: 手順0の答え・攻めた範囲・見つかった穴・根本原因・直したこと・残したこと・もう一度攻めた結果。
**鍵の値や、試して見えた個人の情報は記録に書かない**（伏せる）。

最後に 仕事の `README.md` の進み具合の「9 攻撃して直す」に ○ と日付を入れ、「ひと通り終わりました。直したい所は、図面（docs）から直します」と伝える。

## 入っていれば使える公式の道具（無くても回る）

- Claude Code の組み込みの `/security-review`（変えた所の点検）
- Claude Code の公式プラグイン `claude-security`（たくさんの AI で穴を探し、確かめ、直し案まで出す）・`security-guidance`（危ない書き方を知らせる）。公式の目録から入れる
- Codex の `codex-security`
- 動いているものに実際に攻撃を試す、別の専用の道具もある。使う時は、その道具のライセンスと使い方の決まりを読んでから、別に入れる（このプラグインには入っていない）

## 共通の決まり（どの段でも）

- **設計を変える時は、先に図面（docs）を直してからコードを直す**
- **直す前に、なぜそうなったか（根本原因）を説明してから直す**
- **分からないことは作らずに聞く**。1問ずつ、AI の推奨を添えて聞く（`grill` スキルが入っていれば使う）
- **鍵（パスワード・API キー・トークン・.env の中身）を docs にもコードにも書かない**。書くのは「どこに置いたか」だけ
- **段の終わりは、本人の OK が出るまで次の段へ進まない**。AI が推奨で決めた所は「（推奨で決めた・本人の確認待ち）」と書き、OK をもらったら外す。方向を変えたいと言われたら、その段か前の段の docs から直す
- **段が進んだ・決めたことがあった時は、仕事の `README.md` を直す**: 進み具合の表と「今の段」を直し、「最近の動き」の一番上に `- 日付: 何をしたか・決めたこと` を1行足す
