# dev-validate ─ 段5 価値の検証（住む人に模型を見てもらう）

本番を作り込む前に、**本当に使われるか・お金を払ってもらえそうか**を確かめます。
作った人は自分の作ったものを良く見がちです。触った人の答えを数で見ます。

> **社内で使う道具なら、この段は飛ばしてかまいません。** `00-コンセプト.md` の進み具合に「飛ばす」と書き、`dev-build` に進みます。

## 始める前に

- `docs/00-コンセプト.md`（誰の困りごとか）と、段4の試作があることを確かめる
- 触ってもらう人を3〜5人決める。**コンセプトの「誰が使うか」に当てはまる人**にする（身内や作った仲間だけにしない）
- 聞いた答えに個人情報が入る時は、名前を書かず「Aさん（総務・30代）」のように書く

## 進め方

1. **聞き取りの台本を作る**（下の型）。本人に見せて、言い回しを直す
2. **触ってもらう**: 説明は最小限にして、「〇〇をしてみてください」とお願いし、黙って見る。迷った所・止まった所を書き留める
3. **5段階で聞く**（下の2問）。数字だけでなく「なぜその数字か」を1文聞く
4. **集計する**: 人数・各段階の人数・割合を表にする
5. **合格線で決める**（下の表）。決めるのは本人。AI は推奨を添える

## 聞き取りの台本（型）

```
1. 今、〇〇（困りごと）はどうしていますか？ 最後に困ったのはいつですか？
2. （試作を渡して）〇〇をしてみてください。（黙って見る）
3. 今の操作で、迷った所はありましたか？
4. 【5段階】これを、どのくらいの頻度で使いそうですか？
   5 毎日 / 4 週に数回 / 3 週に1回 / 2 月に数回 / 1 ほぼ使わない
5. 【5段階】これが明日から使えなくなったら、どう感じますか？
   5 とても困る / 4 困る / 3 どちらでもない / 2 あまり困らない / 1 まったく困らない
6. （売るもの）同じことに、今お金を払っていますか？ いくらなら払ってもよさそうですか？
   （ここで出た金額は段7の価格の材料にする。値段を決める場ではない）
7. ほかに、こういう道具があれば使いたい、という人を知っていますか？
```

## 合格線（目安）

「無くなったら困るか」で「5 とても困る」と答えた人の割合で見ます（よく使われる目安は4割）。

| 「とても困る」の割合 | 判断の推奨 |
|---|---|
| 4割以上 | 次へ進む（段6 本番の実装） |
| 2割〜4割 | 迷った所・理由を見て直し、もう一度聞く（段3 画面 か 段4 試作 に戻る） |
| 2割未満 | 困りごとの見立てが違うかもしれない。段1 コンセプトに戻る |

人数が少ないので、数字は目安です。**理由の1文**の方が大事なことも多いので、必ず並べて見せます。
「毎日使うか」が低くても「とても困る」が高いもの（月に1回だが無いと困る、など）はありえます。両方を見て判断します。

## `05-検証.md` の型

```markdown

## 3. 5段階の結果
| 問い | 5 | 4 | 3 | 2 | 1 | 「5」の割合 |
|---|---|---|---|---|---|---|
| どのくらい使うか | | | | | | |
| 無くなったら困るか | | | | | | |

## 4. 理由（1人1文）

## 5. 払ってもよい金額の声（段7の材料）

## 6. 判断
- 判断: 次へ進む / 直して聞き直す（戻る先: ） / コンセプトに戻る
```

## 終わりの確かめ

- `05-検証.md` の 1〜6 に中身がある。6 の判断を本人が決めた
- `00-コンセプト.md` の進み具合の「5 価値の検証」に結果（○ か「戻る」）と日付を入れる
- 次の段を伝える: 進むなら `dev-build`、戻るならその段のスキル

## 共通の決まり（どの段でも）

- **設計を変える時は、先に図面（docs）を直してからコードを直す**
- **直す前に、なぜそうなったか（根本原因）を説明してから直す**
- **分からないことは作らずに聞く**。1問ずつ、AI の推奨を添えて聞く（`grill` スキルが入っていれば使う）
- **鍵（パスワード・API キー・トークン・.env の中身）を docs にもコードにも書かない**。書くのは「どこに置いたか」だけ
