# dev-build ─ 段6 本番の実装（1部屋ずつ施工して検査）

ここから先は、本当に使うものを作ります。家の施工と同じで、**検査の基準を先に決め、1部屋ずつ建て、建てた人とは別の人が検査します**。

AI は「できました」と言います。それを信じるか全部見るかの二択にしないために、
**作る前に掛けた点検表（完成条件）**と、**作った AI とは別の目**を用意します。

## 始める前に

- `docs/01-要件.md`・`02-画面.md`・`03-データ.md`・`04-完成条件.md` を読む
- 段4の試作がある時は、試作をそのまま育てるか、作り直すかを推奨を添えて聞く（試作が「1つの HTML」で、本番に複数人で使うなら作り直しを推奨）
- 作り方（言語・置き先・ログインの仕組み）を1つ推奨して確かめる。決めたら `03-データ.md` に書き足す（図面を先に）

## 1. 完成条件を仕上げる（作る前に）

`docs/04-完成条件.md` に次を足す。**ここが埋まるまでコードを書かない。**

### 1-1. テストの場面の表

1 の表に「本番」の列を足し、次の場面を1行ずつ足す。当てはまらない場面は「なし（理由）」と書く。

| 場面 | 例 |
|---|---|
| ふつうの操作 | 備品を1つ貸し出すと、一覧で「貸出中」になる |
| 境目 | 0件の時・1件だけの時・とても多い時（例: 1,000件）に表示が崩れない |
| まちがった入力 | 空のまま送る・とても長い文字・日付に文字を入れると、分かる言葉で止まる |
| 権限 | 見てはいけない人が、画面からも URL の書き換えでも見られない |
| 同時に操作 | 2人が同じ物を同時に借りようとしても、片方だけが借りられる |
| つながらない時 | 外部サービスが止まっていても、画面が真っ白にならず、分かる言葉が出る |

### 1-2. 守りの条件

- 鍵（API キー・パスワード）がコードにも書庫にも無い
- ログインしないと開けない（社外に出すもの・個人の情報を扱うもの）
- 本人のデータしか見えない（`01-要件.md` の「見てよい人」どおり）
- 本番のデータを、試しの作業で壊さない（試す時は複製で）
- `01-要件.md` の「AI に読ませてはいけないもの」を、AI に送っていない

### 1-3. 誰が確認するか

作った AI とは別の AI（この下の「別の目の点検」）と、人の確かめ役を1人。人の確かめ役は、作った本人以外を推奨する。

本人に完成条件を見せ、OK をもらってから作り始める。

## 2. 1部屋ずつ作る

- 1つの機能（1部屋）ずつ作る。作ったら、その部屋に関わる完成条件の行を自分で試し、○× を付ける
- `02-画面.md` に無い画面・ボタンを足さない。足したくなったら、先に図面を直して本人に確かめる
- 外部サービスにつなぐ所は、そのサービスの公式の説明書で仕様を確かめてから書く（推測で書かない）
- 鍵は `03-データ.md` に書いた保管場所から読む。コードには「ここで鍵を読む」という形だけを書く

## 3. 別の目の点検

作った AI は、自分の作ったものの穴に気づきにくい。**新しい AI を起こし、何も先入観のない状態で読ませます**。
専用の「点検役」の部品は使いません。どの AI の道具でもできるやり方です。

### 起こし方

- **Claude Code**: サブエージェント（別の AI に仕事を頼む仕組み）を新しく起こし、下の依頼文を渡す。点検役は2人、同時に起こす（作りを見る役・守りを見る役）
- **Codex**: サブエージェントを起こせる設定ならそれを使う。使えない時は、新しいターミナルで `codex exec` を開くか、新しい会話を始め、下の依頼文を貼る
- **どちらでも使える代わり**: 新しい会話（新しいウィンドウ）を開き、同じ依頼文を貼る。前の会話の続きで頼まない（先入観が移るため）

### 渡すもの・渡さないもの

- 渡す: 読む場所（docs/ とコードのフォルダ）、完成条件、下の依頼文
- **渡さない: 作った AI の「できました」の報告・自分の考えた結論**（点検役が、それを確かめるだけになってしまうため）

### 依頼文（作りを見る役）

```
あなたは、この道具を作った人とは別の、厳しい点検役です。コードは書き換えないでください。
読む場所: <docs のフォルダ> と <コードのフォルダ>
1. docs/04-完成条件.md の各行を、自分で動かすかコードを読んで確かめ、○×と根拠を書いてください。
   動かして確かめた行と、読んだだけの行を分けてください。
2. docs/01〜03 に書いていないものを作っていないか（作りすぎ）、書いてあるのに作っていないものはないかを見てください。
3. 見つけた問題を、重い順に「重大・高・中・低」で並べ、どこ（ファイルと行）・何が起きるか・直し方の案を書いてください。
「できています」と書く前に、必ず自分で確かめてください。
```

### 依頼文（守りを見る役）

```
あなたは、この道具を攻める側の目で見る点検役です。コードは書き換えないでください。
読む場所: <docs のフォルダ> と <コードのフォルダ>
次を確かめ、見つけた問題を重い順に「重大・高・中・低」で、どこ・誰がどうやって何を得られるか・直し方の案の形で書いてください。
- 鍵（API キー・パスワード・トークン）がコード・設定・docs・記録に書かれていないか
- ログインしないで開ける所、他人のデータが ID の書き換えで見える所はないか
- 入力に仕込まれた文字で、画面やデータベースが乗っ取られる所はないか
- 外に送ってはいけないデータを外へ送っていないか（docs/01-要件.md の「見せてはいけない」「AI に読ませてはいけない」）
- 古くて穴のある部品を使っていないか
理屈の上の心配と、実際に刺さる穴は分けて書いてください。
```

## 4. 根本原因を説明してから直す

点検で問題が出たら、**すぐ直さない**。先に次の3つを本人に短く説明する。

1. 何が起きているか（症状）
2. なぜ起きたか（根本原因。「ここを直せば消える」ではなく「なぜこう作ってしまったか」まで）
3. どう直すか・ほかに同じ原因の所はないか

直すのは点検で出た所だけ（ついでに範囲を広げない）。直し方が図面を変えるなら、先に docs を直す。

## 5. 合格まで回す

- **合格: 「重大」と「高」が0件**。「中」「低」は `docs/reviews/` の記録に残し、本人と直すか決める
- 直したら、**また新しい AI を起こして**点検する（前の点検役に「直しました」と言って確かめさせない）
- 3回回しても合格しない・点検役同士の言うことが食い違う・指摘が間違いだと思う根拠がある → 止めて、指摘と反論を並べて本人に判断してもらう

## 6. 終わったら

- 点検の結果を `docs/reviews/<日付>-本番.md` に残す（点検役ごとの指摘・直したこと・残したこと）。鍵の値が指摘文に入っていたら、伏せてから残す
- 完成条件の「本番」の列が全部 ○、人の確かめ役が確かめた
- `00-コンセプト.md` の進み具合の「6 本番の実装」に ○ と日付を入れる
- 次の段を伝える: 売るものなら `dev-pricing`（段7 価格）、社内の道具なら `dev-design`（段8 デザイン）

## 入っていれば使える公式の道具（無くても回る）

- Claude Code の公式プラグイン `feature-dev`（調べる→設計→実装→点検の流れ）・`code-review`、組み込みの `/code-review`・`/security-review`
- 公式プラグイン `security-guidance`（危ない書き方をした時に知らせてくれる）
- Codex の `codex-security`

これらは「別の目の点検」に**足して**使う。代わりにはしない（作った AI と同じ会話の中で動くものは、先入観が残るため）。

## 共通の決まり（どの段でも）

- **設計を変える時は、先に図面（docs）を直してからコードを直す**
- **直す前に、なぜそうなったか（根本原因）を説明してから直す**
- **分からないことは作らずに聞く**。1問ずつ、AI の推奨を添えて聞く（`grill` スキルが入っていれば使う）
- **鍵（パスワード・API キー・トークン・.env の中身）を docs にもコードにも書かない**。書くのは「どこに置いたか」だけ
