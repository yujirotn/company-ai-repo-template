# dev-concept ─ 段1 コンセプト（施主の要望を聞く）

家を建てる前に、住む人の暮らしと困りごとを聞くのと同じです。ここでは**作り方は考えません**。
「誰が・何に困っていて・どうなればうれしいか」だけを決めます。

## 進め方

1. 本人が仕事の場所を示したら、そのフォルダを使う。新しい仕事には書庫の `projects/<仕事の名前>/` を作り、仕様はその中の `docs/` に置く。**仕事の名前は本人に日本語で付けてもらう**（例: `備品の貸し出し記録`）。AI が勝手に決めたり英語に直したりしない。本人が迷ったら、中身が分かる短い日本語の案を2〜3出して選んでもらう。フォルダ名に使えない記号（`/` `:` など）だけは外し、空白は使わない。コマンドでこのフォルダを扱う時は、パスを必ず `"` で囲む
2. 下の「聞くこと」を、**1問ずつ**聞く。答えを聞いてから次を決める。各質問に AI の推奨か例を添える（「私ならこう考えます。合っていますか？」）
   - 本人から渡された指示書に答えがあれば使い、不足分だけ聞く。試験で推奨を採用した項目は、指示書の回答と区別して記録する
   - `grill` スキルが入っていれば、その進め方を使ってよい
3. 仕事のフォルダに `README.md`（下の型）を作る。次に、答えが出るたびに `00-コンセプト.md` に書き足す（最後にまとめて書かない。途中で止まっても残るように）
4. 本人が答えられない所は空けず「（未定）」と書き、何が分かれば決まるかを1行添える
5. 推測で書いた所には「（推測）」と付ける

## 聞くこと（この順で）

1. **誰が使うか**: 役割と人数（例: 総務の2人と、借りる社員30人）
2. **今、何に困っているか**: 具体的な場面を1つ（例: 誰がプロジェクターを持っていったか分からず、探すのに毎回10分かかる）
3. **今はどうしのいでいるか**: 紙・表計算・チャット・既存の道具・既存の AI など。それの何が不便か
4. **どうなればうれしいか**: 1文で（例: 今どこに何があるかが、開けば5秒で分かる）
5. **種類**: 社内で使う道具か、売るもの（社外の人がお金を払う）か
   - 売るものなら追加で聞く: 同じ困りごとに、今お金を払っている人はいるか（払っている先・金額の目安）。それが「お金になる」証拠になる
6. **やらないこと**: 最初は作らないもの（例: 予約の機能、スマホのアプリ）。作りすぎを防ぐため、必ず1つ以上決める
7. **最初のゴール**: いつまでに、何ができれば一区切りか

## 型（`00-コンセプト.md`）

```markdown
# コンセプト

> 誰の、どんな困りごとを、どう解くか。作り方はまだ書かない。

## 1. 誰が使うか

## 2. 今の困りごと（具体的な場面）

## 3. 今のしのぎ方と、その不便な点

## 4. どうなればうれしいか（1文）

## 5. 種類
- 種類: 社内で使う道具 / 売るもの
- （売るものなら）お金が払われている証拠:

## 6. やらないこと（最初は作らないもの）

## 7. 最初のゴール（いつまでに・何ができれば）

```

## 型（仕事の `README.md`）

仕事の入口です。人が開いても、AI が `dev-start` で読んでも、今の状態と経緯が分かるようにします。

```markdown
# <仕事の名前>

<何の仕事か・誰のためか を1〜2行>

- 種類: 社内で使う道具 / 売るもの
- 今の段: 1 コンセプト
- 次にすること: 

## 進み具合
| 段 | 状態 | 日付・メモ |
|---|---|---|
| 1 コンセプト | | |
| 2 仕様 | | |
| 3 画面 | | |
| 4 試作 | | |
| 5 価値の検証 | | （社内の道具なら「飛ばす」） |
| 6 本番の実装 | | |
| 7 価格 | | （社内の道具なら「飛ばす」） |
| 8 デザイン | | |
| 9 攻撃して直す | | |

## 最近の動き
- <日付>: 仕事を始めた（段1 コンセプト）

## 決まっていないこと
- 

## 中にあるもの
- `docs/` 仕様（00 コンセプト〜06 価格）・`docs/reviews/` 点検と攻撃の記録
- `prototype/` 試作・`app/` 本番
```

社内で使う道具なら、5 と 7 の状態に「飛ばす」と書く。

## 終わりの確かめ

- 7つの見出しすべてに中身がある（「（未定）」は可。ただし 1・2・5 は未定にしない）
- 本人に全文を見せ、「これで次に進んでよいですか？」と聞いて OK をもらう
- OK が出たら、進み具合の「1 コンセプト」に ○ と日付を入れ、次は `dev-spec`（段2 仕様）だと伝える
- 試験で本人の確認を省くよう指示されたら「試験・本人の確認待ち」と記録する。指示書の回答や AI が採用した推奨は、できた docs への承認とは別に扱う

## 共通の決まり（どの段でも）

- **設計を変える時は、先に図面（docs）を直してからコードを直す**
- **直す前に、なぜそうなったか（根本原因）を説明してから直す**
- **分からないことは作らずに聞く**。1問ずつ、AI の推奨を添えて聞く（`grill` スキルが入っていれば使う）
- **鍵（パスワード・API キー・トークン・.env の中身）を docs にもコードにも書かない**。書くのは「どこに置いたか」だけ
- **段の終わりは、本人の OK が出るまで次の段へ進まない**。AI が推奨で決めた所は「（推奨で決めた・本人の確認待ち）」と書き、OK をもらったら外す。方向を変えたいと言われたら、その段か前の段の docs から直す
- **段が進んだ・決めたことがあった時は、仕事の `README.md` を直す**: 進み具合の表と「今の段」を直し、「最近の動き」の一番上に `- 日付: 何をしたか・決めたこと` を1行足す
