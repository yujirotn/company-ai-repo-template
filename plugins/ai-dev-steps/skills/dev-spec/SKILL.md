# dev-spec ─ 段2 仕様（要望書・構造と設備の仕様）

要望を聞いたら、次は要望書と、構造・設備の仕様です。ここで「何を作り、何を作らないか」と「データをどこから取り、どこに置くか」を決めます。

考え方は、画面づくりでよく使われる「体験の5つの層」（戦略 → 要件 → 構造 → 骨格 → 見た目）のうち、下の3つです。骨格（画面）は段3、見た目は段8で決めます。

| 層 | 決めること | 書く場所 |
|---|---|---|
| 戦略 | 何のための道具か・使う人は何を得るか | `01-要件.md` の 1〜2 |
| 要件 | 誰が何を見て何を決めるか・作るもの／作らないもの | `01-要件.md` の 3〜6 |
| 構造 | データの出どころ・置き場所・鍵の置き場所・誰が見られるか | `03-データ.md` |

## 始める前に

- `docs/00-コンセプト.md` を読む。無ければ書かずに「先に dev-concept をやりましょう」と伝える
- `01-要件.md`・`03-データ.md` がすでにあれば、上書きせず、空いている所だけ埋める

## 進め方

1. コンセプトから分かることは、先に下書きとして書き、「（コンセプトから）」と付けて本人に確かめる。**分かっていることを聞き直さない**
2. 分からない所だけ、**1問ずつ**聞く。各質問に推奨を添える
3. 答えが出るたびにファイルに書き足す
4. 曖昧な言葉（「速く」「簡単に」「たくさん」）が出たら、数で言い直してもらう（例: 「速く」→「開いて3秒以内」）

## `01-要件.md` の型

全社共通の `start-from-spec` と同じ見出しの 1〜5 に、6 を足したものです。

```markdown
# 要件

> 誰が何を見て、何を決めるか。誰が見てよいか・見せてはいけない数字は何かを先に書く。

## 1. 何のための仕事か
（戦略: 1〜2文。使う人が何を得るか）

## 2. 誰が使うか
（役割・人数・使う場面。パソコンかスマホか）

## 3. 誰が何を見て、何を決めるか
| 使う人 | 見るもの | 決めること・すること |
|---|---|---|

## 4. 誰が見てよいか・見せてはいけない数字
（金額・個人情報・社外秘など。AI に読ませてはいけないものもここに）

## 5. 最初のゴール（いつまでに・何ができれば）

## 6. 作るもの・作らないもの
| 作る（最初の版） | 作らない（後で考える） |
|---|---|
```

## `03-データ.md` の型

```markdown
# データ

> データの出どころと保存先を先に書く。接続キー（APIキー・パスワード）の**値そのものは書かない**。
> 「どこに保管するか」だけを書く（書庫には入れない）。

## 1. データの出どころ
| データ | どこから来るか（人が入れる・既存の表・外部サービス） | どのくらいの量か |
|---|---|---|

## 2. 必要な接続キー（値は書かない。保管場所だけ書く）
| つなぐ先 | 何のキーか | 許可の範囲（読むだけ等） | 保管場所 |
|---|---|---|---|

## 3. データの保存先・誰が見られるか

## 4. 消す・直す時の決まり
（間違えて入れた時に誰が直せるか・どのくらいの間とっておくか）
```

接続キーは「読むだけ」など、**できるだけ狭い許可**を推奨する。保管場所は、パソコンの鍵の保管庫（Mac のキーチェーンなど）やパスワード管理の道具、公開して動かす時は置き先の秘密の保管場所を推奨し、`.env` は書庫に入れない前提で使う。

## 終わりの確かめ

- `01-要件.md` の 1〜6、`03-データ.md` の 1〜4 に中身がある
- 「作らない」が1つ以上ある
- 鍵の値らしき文字列（長い英数字の並び・`sk-`・`ghp_` などで始まるもの）が docs に無い
- 本人に見せて OK をもらったら、`00-コンセプト.md` の進み具合の「2 仕様」に ○ と日付を入れ、次は `dev-wireframe`（段3 画面）だと伝える

## 共通の決まり（どの段でも）

- **設計を変える時は、先に図面（docs）を直してからコードを直す**
- **直す前に、なぜそうなったか（根本原因）を説明してから直す**
- **分からないことは作らずに聞く**。1問ずつ、AI の推奨を添えて聞く（`grill` スキルが入っていれば使う）
- **鍵（パスワード・API キー・トークン・.env の中身）を docs にもコードにも書かない**。書くのは「どこに置いたか」だけ
