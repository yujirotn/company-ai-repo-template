# 書庫に保存する

**本体（`main`ブランチ）に直接保存しない。** 必ず次の順番で進める:
分かれ道を作る（ブランチ）→ 保存する（コミット）→ 取り込んでもらう案（プルリクエスト）→ 人が確認して取り込む。

## 用語（初めての人向け）

- **ブランチ**: 本体に影響を与えずに作業できる、分かれ道のようなもの
- **コミット**: 変更内容を「ここまでの分」として記録すること
- **プルリクエスト（PR）**: 「この変更を本体に取り込んでください」という提案。人が見てから取り込む
- **マージ**: プルリクエストの内容を本体に取り込むこと

## 手順

1. 今の状態を確認する: `git status` で、何が変わったかを見る
2. 秘密が混ざっていないか確認する: `.env` や鍵ファイルが `git status` に出ていたら、
   絶対に追加しない。`.gitignore` に入っているか確認する
3. 分かれ道を作る（まだ作っていなければ）:
   ```bash
   git switch -c <わかりやすい短い名前>/<やったことの要約>
   ```
   例: `git switch -c feature/画面-進捗表示`
4. 変更をコミットする（ファイルを選んで追加する。`git add -A` のような無差別追加はしない):
   ```bash
   git add <変更したファイル>
   git commit -m "<種類>: <何をしたか・1行>"
   ```
   種類の例: `feat`（新機能）`fix`（修正）`docs`（文書）`chore`（雑務）
5. 書庫に送る:
   ```bash
   git push -u origin <ブランチ名>
   ```
6. プルリクエストを作る（GitHubのウェブ画面、または `gh pr create` コマンド）。
   タイトルと「何を・なぜ変えたか」を書く
7. **人が確認してから取り込む（マージする）。AIが自分でマージまで進めない**
   （指示で明確にマージまで頼まれた場合を除く）

## してはいけないこと

- `main` ブランチに直接コミット・プッシュする
- `git push --force`（履歴を書き換える、取り消せない操作）を使う
- 確認なしにプルリクエストをマージする
- 秘密ファイル（`.env`・鍵ファイルなど）をコミットに含める

## 迷ったとき

分かれ道の名前が思いつかない・コミットをどう分けるか迷う・プルリクエストの説明の書き方が分からない、
などで迷ったら、作業を止めて人に聞く。
