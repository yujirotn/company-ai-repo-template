# design-review ─ 見た目の仕上がりを点検する

**目的は「会社の決まりどおりに、崩れずに見えているか」を、実際の表示で確かめること**。好みで直さない。決まりに書いてあることと、誰が見ても崩れていることだけを指摘する。

## いつ使うか

| 場面 | 使う？ |
|---|---|
| Webページ・LP・画面を人に見せる前、公開する前 | ✅ |
| 資料・スライド（HTML・PDF・画像）を人に出す前 | ✅ 幅の確認は資料の大きさで読み替える |
| 「なんか素人っぽい」「崩れている」と言われた | ✅ 原因を見つけて、直す順番を決める |
| 迷わず使えるか・手数が多くないか | ❌ `ux-review` |
| タイトル・説明文・リンク切れ・ダミー文字の残り | ❌ `web-preflight`（先に通しておく） |

## 手順

### 1. 物差しをそろえる（★作る前・見る前に読む）

1. この書庫の一番上の `DESIGN.md`（会社のデザインの決まり）を読む。色・書体・文字の大きさ・余白・ロゴ・使わないもの・見本を確かめる
2. 仕事ごとの決まり（`projects/<名前>/docs/02-画面.md` など）があれば読む。会社の決まりとぶつかる時は、仕事ごとの決まりを優先し、そう判断したことを記録に残す
3. `DESIGN.md` に【　】が残っていて判定に必要な項目は、勝手に決めずに1問ずつ聞いて埋める（埋まるまでは、その項目を「未判定」にする）
4. 点検する範囲を決める。新しく作ったものは全体、直したものは直した所と、その影響が出る所

### 2. 表示して撮る（★コードだけで判定しない）

- Webページ・画面は、**PC（1280px 前後）・中間（768px 前後）・スマホ（375px）**の3つの幅で、上から下まで全部を見る
  - `ux-review` の `scripts/ux_measure.py` を使うと、3つの幅のスクショがまとめて撮れる
  - ボタンの上にポインタを乗せた時・キーボードで選んだ時・メニューを開いた時の見た目も、実際に動かして見る
- 資料・スライドは、全ページを実際の大きさで開いて見る
- 撮った画像は作業用の一時フォルダに置く（書庫に残さない）

### 3. 観点ごとに判定する

`references/checklist.md` の観点を、1つずつ **合格／不合格／未判定** で判定する。
境目で迷ったら不合格側に倒し、「境目」と書き添える（あとで決まりに書き足すきっかけになる）。

色の読みやすさ（文字と背景の明るさの差）は、`scripts/contrast.py` で数字を出して確かめてよい。

```bash
python3 <このスキルのフォルダ>/scripts/contrast.py "#333333" "#ffffff"
```

### 4. 報告する

冒頭に観点ごとの判定の表を置き、その下に直すべき点を1件ずつ書く。

```
[不合格] 観点 — 場所（ページ・幅・要素）
何が起きているか: 実際に見えたこと
決まり: DESIGN.md のどの項目か（無ければ「誰が見ても崩れている」理由）
直し方: 1つ
```

- 判定の記録（対象・見た幅・各観点の判定・残った課題）は、その仕事の `docs/` に残す
- このスキルは**点検**まで。直すのは作る側の作業として分ける（自分で作ったものを自分で点検した時は「自己点検」と書き、別の人や別のAIの点検と区別する）
- 公開・納品・外部への送信は、このスキルでは行わない。必要なら依頼した人に確かめてから

## やらないこと

- コードやデザインファイルだけを見て合格にする（必ず表示して見る）
- `DESIGN.md` に無い色・書体・飾りを、レビューのついでに持ち込む
- 好みで直す（「もっとおしゃれに」は指摘にしない）
- 今ある正式なページを、レビューを理由に作り直す

## 関連

- `references/checklist.md`（観点と合格の境目）
- `scripts/contrast.py`（文字と背景の読みやすさを数字で出す）
- 一番上の `DESIGN.md`（会社のデザインの決まり）
