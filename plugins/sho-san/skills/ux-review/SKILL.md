# ux-review ─ 分かりやすさを実測で点検する

**目的は「使う人が迷わず・覚えずに・間違えずに作業を終えられるか」**。好みの話はしない。

良い画面は**作る前に**ほぼ決まる。作った後のレビューだけだと、画面の組み立て（何を主役にし、何を置かないか）が固まっていて、細かい欠陥を潰すことしかできない。
「大きな問題が0件」は「壊れていない」の証明であって、「使いやすい」の証明ではない。だから、設計を先に置く。

## 2つのやり方

| やり方 | いつ | 出すもの |
|---|---|---|
| **① 設計** | 画面を作る**前** | 画面設計シート（`references/screen-design-sheet.md` の型）。主な作業1つ・置く/置かないもの・お手本・合格条件 |
| **② レビュー** | 画面を作った**後** | 設計シートの合格条件に対する判定と、直すべき点の一覧 |

画面を作る仕事なら、①を先にやる。この書庫の仕様書（`projects/<名前>/docs/02-画面.md`）がある時は、設計シートの中身をそこに書くか、そこから参照する。

## いつ使うか

| 場面 | 使う？ |
|---|---|
| 画面を含むものを作る前の設計 | ✅ ①設計 |
| 画面を含むものを作った後のレビュー | ✅ ②レビュー |
| 試作・管理画面が「分かりにくい」と言われた | ✅ 原因を見つけて、直す順番を決める |
| 資料のHTML（図解・提案書）が読みにくい | ✅ 読む順番・情報量の観点で見る |
| 色・余白・文字の大きさの仕上がり | ❌ `design-review` |
| 正しく動くか・安全か | ❌ コードのレビュー・テストの担当 |

## ① 設計のやり方

1. 使う人・開く理由・主な作業（1つ）を決める。決まらなければ依頼した人に聞く
2. **お手本にする既存の画面を必ず1つ選ぶ**（新しい型を発明しない。借りた型は外れにくく、発明した型は事故が起きやすい）。必要なら実物を Web で確かめる
3. 最初に見える範囲（スクロールする前）に置くもの（上から3つ）と、置かないもの（別の画面・折りたたみに回すもの）を決める
4. 合格条件を数字で書く（主な作業の手数の上限・操作要素の数の上限・スマホ幅 375px で終わるか）
5. シートを依頼した人に見せ、できればクリックできる試作を触ってもらってから作り始める

## ② レビューのやり方

### 前提（★満たさなければレビューしない）

- **画面が起動していて、URL かファイルで開ける**こと。スクショやコードだけで判定しない。開けなければ「起動していないのでレビューできない」と返す
- 画面設計シートがあること。無い時（今ある画面の改善など）は、①の1〜4をその場で決めてから判定する
- 判定の軸は**設計シートの合格条件**。直すべき点の重さだけで合格にしない

### 1. 前提を3つ決める（★推測しない）

| 項目 | 例 |
|---|---|
| 使う人 | 営業（外出先でスマホ）／事務（PC・1日に何度も）／管理者（承認だけ） |
| 主な作業（3つまで） | 今日やる仕事を見つけて完了にする／担当を決める／期限切れを確かめる |
| 対象 | URL・HTMLファイル・変更の差分 |

分からなければ依頼した人に聞く。主な作業が決まらないと、レビューはただの感想になる。

### 2. 撮って数える

```bash
python3 <このスキルのフォルダ>/scripts/ux_measure.py "<URL か HTMLファイル>" "<出力フォルダ>" --wait 1500
```

- 出力フォルダは、作業用の一時フォルダにする（書庫の中に画像を残さない）
- 画面の描画に時間がかかる時は `--wait` を増やす
- 数えるのは最初に見える範囲（スクロール前）だけ。**人が最初に見る範囲が判定の主戦場**
- 数値の読み方は `references/principles.md` の「計測の目安」
- このスクリプトは Playwright（ブラウザを自動で動かす道具）を使う。入っていなければ `pip install playwright && playwright install chromium` を本人に確かめてから入れる。入れられない時は、ブラウザで 1280px と 375px の画面を開いて撮り、同じ項目を目で数える

### 3. 目で見る（★省かない）

- 撮った `ux-1280.png`・`ux-375.png` を実際に開いて見る
- **最初に目に入る3つ**を書き出す。スクリプトの `first_seen` と食い違ったら、目で見た方を正とする
- 主な作業を**実際に操作して**、手数（クリック・入力・画面の行き来）を数え、設計シートの上限と比べる。操作はブラウザの自動操作で行ってよい。操作できなかったら合格にしない

### 4. 12の観点で判定する

`references/principles.md` の U1〜U12 のチェックを当てる。「いいえ」が付いたものを候補にし、**つまずく場面**（誰が・何をしようとして・どこで迷うか）が書けたものだけを、直すべき点として出す。

### 5. 報告する

- **冒頭に合格条件の表を置き、各条件を「満たす／満たさない（実測の値）」で書く**。1つでも満たさなければ、直すべき点が軽いものだけでも「不合格」とする
- 直すべき点は、次の形で1件ずつ書く

```
[重さ] 観点（U番号）— 場所
つまずく場面: 誰が・何をしようとして・どこで迷うか
根拠: 観点のチェックのどれに当たるか
直し方: 1つ
```

- 重さの目安: **重い**＝主な作業が終わらない・取り返しのつかない誤操作が起きる／**中くらい**＝終わるが迷う・手数が上限を超える／**軽い**＝慣れれば困らない
- 直し方は「減らす → 隠す（折りたたむ・別の画面へ） → 順番を変える → 言葉を変える → 足す」の順に考える。足すのは最後
- 画面だけでは判定できないこと（テストの進め方など）は、最後に「提案」として添える
- 「実際に使う人3〜5人に試してもらうのが一番確か」と必ず添える

## やらないこと

- 数値だけで合格・不合格を決める（数値は目で見るきっかけ）
- 起動していない画面を、スクショとコードだけで合格にする
- お手本なしで新しい画面の型を発明する
- 根拠の観点が言えない指摘を出す
- 要件そのもの（何を表示するか）を勝手に削る提案で終わる。要件とぶつかる時は両方を並べて、依頼した人に決めてもらう
