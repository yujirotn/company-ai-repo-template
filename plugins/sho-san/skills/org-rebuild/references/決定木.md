# 決定木 ─ どの会社でも聞く質問（順番どおり）

上から順に聞く。上の答えが下の質問を決める（依存の順）。
各論点の「例」は**架空の会社（従業員20人の工務店「A社」）**の答え。**相手には例として見せるだけで、答えは相手が決める**。

各論点の書き方:
- **聞くこと**: そのまま読み上げられる質問文
- **先に調べる**: 聞く前に自分で集める事実（相手に聞かない）
- **推奨の考え方**: 推奨を作るときの軸
- **例**: 架空の A社の答え

時間が無い時（30分版）は、0 を入口にして、点検で一番低かった柱に当たる論点を2〜3個だけ選ぶ。

| 点検で低かった柱 | 先に聞く論点 |
|---|---|
| 土台（指示・置き場所） | 1・2・10 |
| 安全 | 13・15・16 |
| 育つ仕組み | 8・11・14 |
| 任せ方 | 9・12・18 |

---

## 0. 入口: ハーネス点検の結果
- **聞くこと**: 「点検の結果は◯点、型は『◯◯』でした。『次に直す項目』のうち、気になるものはありますか？」
- **先に調べる**: 点検レポートの4本の柱（土台・安全・育つ仕組み・任せ方）の達成率と「次に直す項目」
- **推奨の考え方**: 点数の一番低い柱を、以下の論点のどこで直すかを先に示す（上の表）
- **例**: 72点「土台は強いが、安全が薄い型」→ 論点 13・15・16 から

## A. 何の仕事をしているか

### 1. 仕事の領域
- **聞くこと**: 「今の仕事を大きく分けると何ですか？」→ 返ってきた一覧に対し「◯◯（フォルダにはあるのに挙がっていない領域）はどう扱いますか？」
- **先に調べる**: 今のフォルダのトップ階層と件数・容量、最近1か月に動いたもの
- **推奨の考え方**: 本人の口から出た領域を正にする。フォルダにあって口から出ないものは「やめたのか言い忘れか」を必ず聞く（メタ認知の指摘）
- **例**: 本人が挙げたのは「営業・施工管理・社内」の3つ。フォルダには「採用」（40件）もあった → 聞いたら「残す」。4領域になった

### 2. 置き場所の基準
- **聞くこと**: 「見積や提案書など、お客様ごとに作るものはどこに置きたいですか？」
- **先に調べる**: 1つの取引先が複数の領域にまたがっている例
- **推奨の考え方**: 基準は1つに絞る。「資料にお客様の名前が入るなら `projects/<お客様>/`」。例外は少なく明示する。提案と納品を分けると受注で引っ越しが要るので、同じフォルダの中に置く。本人が会社の書庫にも入れたいと言った時は、その書庫の「置き場所の3段」（会社／プロジェクト／個人）に当てはめる
- **例**: お客様の名前が入るなら `projects/<お客様>/`。例外は「展示会の資料は営業の型として `plugins/eigyo/`」

### 3. 領域とプロジェクトの役割
- **聞くこと**: 「領域のフォルダには何を置きますか？ 型（使い回すもの）と、実作業のどちらですか？」
- **先に調べる**: 毎回ゼロから作っている仕事（同じ種類の資料がお客様ごとにバラバラにある）
- **推奨の考え方**: 領域＝型（`plugins/<部署名>/` のスキルや雛形）、プロジェクト＝実作業。2件目で型を使い回せるか、で判断する
- **例**: 見積書の型が無く、毎回前の見積をコピーしていた → 型を1つ抜き出して部署の道具にする宿題にした

## B. 器（書庫と保存先）

### 4. 作り直し方式と履歴
- **聞くこと**: 「新しい書庫を作り直しますか、今の書庫で整理しますか？ 古い履歴は残しますか？」
- **先に調べる**: 書庫の容量と `.git` の容量、コミット数、リモートの有無、他に使っている人や会話
- **推奨の考え方**: 履歴が重い・構造を大きく変えるなら新しい書庫＋履歴の要約（`HISTORY.md`）＋古い書庫は archive（読み取り専用で残る）。小さければ今の書庫で整理
- **例**: 作業 3GB のうち `.git` が 2GB → 新しい個人の書庫を作り、古い書庫は archive

### 5. 置き場の場所
- **聞くこと**: 「新しい書庫はどこに置きますか？（GitHub の名前・手元の場所）」
- **先に調べる**: 自動同期をするか（macOS では「デスクトップ」「書類」「ダウンロード」がバックグラウンドの処理から守られていて、定期実行が権限エラーで落ちることがある）
- **推奨の考え方**: 手元は `~/projects/<名前>` など守られたフォルダの外。GitHub に上げるなら、個人のハーネスは本人のアカウントに Private。みんなに配りたいものだけ、本人が希望すれば会社の組織の書庫に入れる
- **例**: 会社の組織の下に `a-sha-ai`（Private）／手元は `~/projects/a-sha-ai`

### 6. 重いものの置き場と線引き
- **聞くこと**: 「動画・画像・PDF など重い資料は、どこに置きますか？ どこで線を引きますか？」
- **先に調べる**: 拡張子ごと・フォルダごとの容量、Drive 等が手元に見えているか（マウント）と空き容量、Drive に既にあるフォルダ
- **推奨の考え方**: 種類で分ける（拡張子は `.gitignore` で機械的に守れる）。保存先は書庫と同じフォルダ名で揃える。素材は保存先に置いたまま扱う。大量の個人データも保存先へ
- **例**: 現場写真・図面 PDF は共有ドライブの同じフォルダ名の下。書庫には文字のファイルだけ

### 7. 仕分けのルール
- **聞くこと**: 「残すもの・アーカイブするものを、どう決めますか？」
- **先に調べる**: フォルダごとの最終更新日（README の更新日と git の最終コミット）
- **推奨の考え方**: 「直近 N 日に動いたものを残す」をその回だけの基準にして、残す側の表だけを見せる。型や教材は日付が古くても「今も使っているか」を個別に聞く。**今後の自動アーカイブはしない**
- **例**: 3か月で機械的に分け、表を見せて1つずつ直してもらった

### 8. 共通フォルダ（タスク・議事録・調べもの・メンバー）
- **聞くこと**: 「タスク管理・議事録・調べもの・メンバー管理のフォルダは、実際に使っていますか？」
- **先に調べる**: 各フォルダの最終更新と、それを書いている仕組み（定期実行・hook・スキル）
- **推奨の考え方**: 使っていないなら廃止。ただし「誰がいるか」は1か所（この書庫なら `members/` の名札）にまとめる。タスクの入口は1つに絞る
- **例**: 議事録フォルダは半年動いていなかった → 廃止。タスクは今使っているタスク管理ツールに一本化

## C. AI の体制

### 9. 役割ごとの AI（ペルソナ・エージェント）の要否
- **聞くこと**: 「役割ごとの AI に、何を期待していましたか？」（複数選択: 別の目で穴を指摘／専門知識で質を上げる／並列で進める／話し相手のキャラ）
- **先に調べる**: 各エージェントが実際に動いた記録（作業フォルダの最終更新・担当欄の件数）
- **推奨の考え方**: サブエージェントが効くのは「コンテキストを分ける・独立した目・道具を制限・並列」の4つだけ。人格や口調はほぼ効かない。専門知識はスキルと領域の指示ファイルに移す
- **例**: 8つのキャラ → 役割名のエージェント2つ（レビュー役・セキュリティ役）

### 10. 専門知識の置き場
- **聞くこと**: 「領域ごとの知識（社内の決まり・やり方・業界知識）はどこに置きますか？」
- **推奨の考え方**: その仕事だけの知識はプロジェクトや領域のフォルダの指示ファイル（そのフォルダを触った時だけ読まれる）、どこでも使う制作の型（文章・デザイン）はスキル。会社の見た目の決まりは `DESIGN.md`
- **例**: 施工の段取りは施工管理のフォルダ、建材の知識は参照資料、広報物の型は全社共通のスキル

### 11. スキルの仕分け
- **聞くこと**: 表（外す／残す／あとで聞く）を見せて「これでよいですか？」→ 気になったものを個別に説明
- **先に調べる**: 各スキルの最終更新と、廃止した仕組みへの依存
- **推奨の考え方**: 廃止した仕組みに紐づくものは外す。相手が「これ何？」と聞いたら、中身と最後に使われた日を答える。残すものは廃止したパスへの参照を書き換える。置き場所は、本人だけ＝個人のハーネスが基本。本人が希望したものだけ、会社の書庫（全員に配る＝`plugins/`、その仕事だけ＝`projects/<名前>/`）に入れる
- **例**: 25本 → 18本。本人が「みんなにも使ってほしい」と言った3本だけ会社の書庫の `plugins/` へ、残りは個人のハーネスに残す

### 12. 自作の道具の置き方
- **聞くこと**: 「スクリプトやエージェントまで持つ自作の道具は、ツール（別の書庫）ですか、AI の作業の仕方（ハーネスの部品）ですか？」
- **推奨の考え方**: 動くアプリは別の書庫＋README だけ。AI の作業の仕方はハーネスの中。配るものは公式の形: 書庫直下 `plugins/` ＋ `.claude-plugin/marketplace.json`。`claude plugin validate` を通す
- **例**: 見積の計算ツールは別の書庫、見積の書き方のスキルは `plugins/eigyo/`

## D. 安全と権限

### 13. 止める仕組みの精査（1つずつ）
- **聞くこと**: 一覧（hook・禁止ルール・確認の設定・運用ルール）に1つずつ「外す／残す」の推奨を付けて見せ、「これでよいですか？」
- **先に調べる**: hook の中身、設定の ask/deny、運用ルール、実際に止められた回数や誤検知
- **推奨の考え方**: 必ず残すのは**他人に届く操作**（メール・チャットの送信・公開）と**取り返しがつかない操作**（main への force push・危険な削除・本番データベースの破壊的な変更）。それ以外の確認は、作業を止めている割に守っていないなら外してよい。止める仕組みが**実際の経路に効いているか**を確かめる（Bash だけを見る hook は MCP 経由の操作を止めない）
- **例**: 毎回のファイル保存の確認は外し、メール送信・本番反映・force push の確認は残した

### 14. 定期で動く仕事
- **聞くこと**: 「毎朝・毎晩・毎週動いている自動の仕事は、実際に読んでいますか？」
- **先に調べる**: クラウドの定期実行・cron・launchd の一覧と、書き込み先（廃止するフォルダに書いていないか）
- **推奨の考え方**: 読んでいないものは止める。代わりの仕組みがあるなら、1週間使ってから作り直すか決める
- **例**: 毎朝のニュースまとめ（誰も読んでいない）を停止

### 15. ログイン情報と決済
- **聞くこと**: 「ブラウザでパスワードを求められたら、AI に自分で入力させますか？ 決済はどう扱いますか？ 端末は離れた場所から操作しますか？」
- **先に調べる**: パスワード管理ツールの有無、端末の前に人がいるか（指紋認証を押せるか）、会社の規程
- **推奨の考え方**: AI に読ませるなら、パスワード管理ツールに AI 専用の保管庫を作り、読み取り専用の鍵で読ませる。鍵はファイルに書かない（OS の鍵の保管場所か `.env`）。**決済は事前に人が確認**（「どこで・何に・いくら」）。カードを AI が読める場所に置くかは、人がいない時に決済まで終える必要があるかで決める（置くなら受け入れたリスクとして記録）
- **例**: ログインは人が入力。決済は AI がやらない

### 16. 秘密情報の検査と持ち出しの止め
- **聞くこと**: 「push の前に、秘密情報の検査を挟みますか？」「取り出した値を外へ送るコマンドを止めますか？」
- **先に調べる**: 新しい書庫に対して gitleaks などを1回走らせ、ヒットの中身を分類（本物／誤検知）
- **推奨の考え方**: push 前の検査は普段の作業を止めないので入れる。「取り出し＋外への送信」を1つのコマンドでつないだ時だけ止める（完全ではないが、一番素直な抜き取りは止まる）
- **例**: push 前に gitleaks を走らせる決まりにした

## E. 回し方

### 17. 同期の頻度
- **聞くこと**: 「GitHub への保存（push）は、いつ・どのくらいの頻度にしますか？」
- **推奨の考え方**: 人がその都度プルリクエストで出すのが基本。自動にするなら定期実行にし、競合したら上書きせず止めて知らせる
- **例**: 作業の区切りごとに枝を作ってプルリクエスト

### 18. 作業の単位
- **聞くこと**: 「仕事ごとに AI の作業場所を開き分けたいですか？」
- **推奨の考え方**: ハーネスは1つの書庫。仕事単位はサブフォルダ（`projects/<名前>/`）を開く（指示ファイルやスキルは上の階層から読まれる）。ただし Claude Code の `.claude/settings.json` は起動した場所のものだけ読まれるので、設定を効かせたい場所に注意する。コードを持つツールは別の書庫。重い並行作業だけ worktree
- **例**: 書庫は1つ。現場ごとに `projects/<現場名>/` を開く

## 道具の分岐（Codex を使っている場合）
- 指示は `AGENTS.md`（`CLAUDE.md` と同じ内容を書くか、どちらかを参照させる）
- 設定は `~/.codex/config.toml`。**設定ファイルの中のトークンは環境変数へ移す**（ハーネス点検で指摘されやすい）
- スキルはプラグインで読み込めるものもある。読み込めない手順は「手順ファイル」を置き、`AGENTS.md` から参照させる
- hook が無い・少ない場合は、論点 13・16 の機械的な止めを sandbox と承認ポリシーで代える
- ※ Codex 側の分岐は机上の整理で、実環境では十分に確かめていない
