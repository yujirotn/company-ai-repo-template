# web-preflight ─ 公開前の機械的な点検

**目的は、人が目で見る前に、機械で見つかる抜けを全部つぶしておくこと**。
人の時間は「見た目」と「使いやすさ」の判断に使う。機械で分かることを人に探させない。

## いつ使うか

| 場面 | 使う？ |
|---|---|
| 静的なHTMLのサイト・LP を公開・納品する前 | ✅ |
| 直したページを、もう一度出す前 | ✅ |
| 見た目の仕上がり | ❌ `design-review`（このスキルの後に行う） |
| 迷わず使えるか | ❌ `ux-review` |
| サーバーで動くアプリ・CMS の画面 | △ 書き出したHTMLや、手元で保存したHTMLなら使える。動いている画面そのものは見られない |

## 手順

### 1. 点検する

```bash
python3 <このスキルのフォルダ>/scripts/web_preflight.py <サイトのフォルダ> --out <作業用フォルダ>/preflight.md
```

- 標準ライブラリだけで動く。**通信はしない**。書き込むのは `--out` に指定したレポートだけ（`--out` を省くと画面に出すだけ）
- 終わりの番号: `0`＝「要修正」なし／`1`＝「要修正」あり、またはフォルダにHTMLが無い／`2`＝使い方の間違い

### 2. 結果を読む

| 重さ | 中身 | どうするか |
|---|---|---|
| **要修正** | タイトル・説明文・スマホ表示の設定（viewport）が無い／手元のファイルへの参照切れ／ダミー文字の残り（Lorem ipsum・ダミー・〇〇・TODO など）／中身の無いリンク（`href=""`・`href="#"`・`javascript:`） | 直す。直さない時は理由を記録に書く |
| **注意** | 言語の指定（`lang`）・SNSで共有した時の表示（OGP）・タブのアイコン（favicon）が無い／大見出し（`h1`）が0個か2個以上／画像の代わりの文字（`alt`）が無い・「画像」「image」などの中身の無い言葉・ファイル名のまま／タイトル・説明文が長すぎる・短すぎる | 1件ずつ、直すか・このままでよい理由を記録に書く。素通りしない |
| **情報** | 見出しの段階が飛んでいる（`h2` の次がいきなり `h4` など）／外部へのリンクの数 | 必要なら直す |

- 「このままでよい」と判断したものは、理由と一緒にその仕事の `docs/` に残す
- 根拠なく「要修正」を除外しない

### 3. 機械では分からないことを、人の目で確かめる

このスクリプトは、次のことを**確かめない**。公開前に別に確かめる。

- 外部のリンク先が本当に開くか（通信しないため）。主なリンクは、実際にブラウザで開いて確かめる
- 見た目・崩れ → `design-review`（PC・中間・スマホの3つの幅で全部を見る）
- 使いやすさ → `ux-review`
- 誤字・脱字、画像の中の文字の間違い → 全ページを目で読む
- フォームの送信・メニューの開閉など、動き → 実際に操作する
- アクセス解析のタグ・問い合わせの送り先が、本番用になっているか → 依頼した人に確かめる

### 4. 公開する前に

- 公開・納品・本番への反映は、このスキルでは行わない。この書庫の決まり（本番を触らない）に従い、依頼した人の許可を取ってから行う
- レポート・点検の記録をそろえて、依頼した人に見せる

## やらないこと

- 「要修正」が残ったまま「点検済み」と言う
- 「注意」を理由なく放っておく
- 点検のついでに、ページの中身やデザインを変える（直すのは作る側の作業として分ける）

## 関連

- `scripts/web_preflight.py`（点検のスクリプト）
- `design-review`（見た目）・`ux-review`（使いやすさ）
