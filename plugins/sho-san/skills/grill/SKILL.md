# grill ─ 計画を1問ずつ詰める

ふわっとした計画・設計・決めごとを、**共通理解に達するまで**詰めていく。
普段の相談が「気づきを促す問い」なら、grill は「**黙って仮定したものを1つも残さない**」ための問い。

> 原典: Matt Pocock の `grilling` / `grill-me` スキル（https://github.com/mattpocock/skills 、MIT License）。
> 日本語の現場向けに書き直した。ライセンス表記は同じフォルダの `LICENSE` を参照。

## 核となる決まり

- **ゴールは共通理解**。作り始めてからの「そういう意味じゃなかった」を、作る前に潰す
- **1問ずつ聞く**。答えを聞いてから次の質問を決める。前の答えで、次に聞くべきことが変わるため
- **各質問にAIの推奨を添える**。「どう思いますか？」で放置しない。「私ならXです。理由は〜。これでよいですか？」の形で聞き、「はい」と答えれば推奨が採用されるように書く
- **根から枝へ降りる**。上の決定（目的・誰のためか）が、下の決定（画面・データ・やり方）を決める。上から順に聞く
- **事実を調べるのはAIの仕事**。書庫のファイル・仕様書・README・コードを見れば分かることを人に聞かない。調べて分かったことは「質問」ではなく「確認」にする（「READMEにはXとありました。今もこれで合っていますか？」）
- **決めるのは人**。決定はすべて人に聞いて、答えを待つ

## 手順

### 1. 何を詰めるかを1行で決める

計画／設計／決めごと／提案 のどれかを1行にする。対象があいまいなら、まずそれを1問で確かめる。

### 2. 先に自分で調べる

聞く前に、答えがすでにある場所を当たる（この書庫の `projects/<名前>/docs/` の仕様書、README、関係するファイル）。
調べものに時間がかかる時は、調べものの結果に左右されない質問から先に聞いてよい。

### 3. 決める順番の地図を見せる

まだ決まっていないことを洗い出し、「どれを先に決めないと、どれが決められないか」の順に並べる。
冒頭で、その地図を**短く**見せる（何問くらいになりそうかの見通しも）。

### 4. 1問ずつ聞く

次の形で1問出し、答えを待つ。

```
❓ Q1 ─ <論点の見出し>: <質問の本文。選択肢があれば並べる>

➡️ 私の推奨: <推奨の答え>。理由: <なぜそれが筋か>
```

- Claude Code なら質問用の道具（`AskUserQuestion`）を使ってよい。推奨を1つ目の選択肢にし、末尾に「（推奨）」と付ける
- 道具が使えない場面（Codex・チャット欄だけの時など）は、上のテキストの形で出す
- 二択で済むものを四択に膨らませない
- 答えがあいまいなら、具体的になるまで同じ論点に留まる
- 答えが前の答えと食い違っていたら、その場で静かに指摘する（「先ほどはXと仰いましたが、今の答えはYに聞こえます。どちらにしますか？」）

慣れてきたら、**お互いに依存しない質問**に限って、まとめて出してもよい（原典の方式）。その場合も1問ずつ番号と推奨を付ける。

### 5. 全部決まったら止める

地図のすべての枝を通って、黙って仮定したものが残っていない状態で終える。だらだら続けない。最後に次の形でまとめる。

```
## 詰め切った結論

### 決まったこと（決めた順）
- 論点1 → 決定 → 理由
- 論点2 → 決定 → 理由

### 残った前提・リスク
（まだ確かめていない前提・やめる条件）
```

**結論を出しても、それに沿って作業を始めない。** 人が「共通理解に達した」と言うまで、作る・送る・発注する、のどれにも進まない。

### 6. 残す

- 仕事（プロジェクト）の計画を詰めた時は、その仕事の仕様書（`projects/<名前>/docs/`）か README に結論を書く
  （`handoff` スキルがあれば使う）
- 書いた後の保存は、この書庫のやり方（枝を作る→コミット→プルリクエスト）に乗せる

## よくある失敗

- 調べれば分かることを人に聞く
- 推奨を添えずに質問だけ投げる
- 前提が決まっていない質問を先に聞く
- 詰めること自体が目的になって、止め時を逃す
