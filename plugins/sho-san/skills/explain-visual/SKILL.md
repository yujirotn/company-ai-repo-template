# explain-visual — 図で分からせる

**目的は「読ませる」ことではなく「分からせる」こと。** 文章で3行を超えるなら、図に置き換えられないかを先に考える。

## 使い分け（先に確かめる）

| 求められているもの | 使うスキル |
|---|---|
| 仕組み・考え方を理解したい（1枚のHTML・図が主役） | **このスキル** |
| 研修・発表でめくる資料が欲しい | `slide-deck-create` |
| 同じ中身を「配る用（A4縦）」と「映す用（16:9横）」の両方で欲しい | `doc-kit` |
| サービスのつながりをロゴ入りの構成図にしたい（エンジニア向け） | `stack-diagram` |
| 見た目の点検・手直しだけ | `visual-design` |

迷ったら「**1回読んで分かればいいもの（このスキル）か／繰り返し見せる資料（スライド）か**」で分ける。

口頭で1〜2行で済む質問、ほかのスライド系スキルが動いている最中には使わない。

---

## 手順

### 0. 会社の決まりを読む

書庫の一番上の `CLAUDE.md`（置き場所・守ること）と `DESIGN.md`（色・書体・使わないもの）を読む。
図の色は `DESIGN.md` に合わせる。`DESIGN.md` に【　】が残っていて色が決まっていない時は、聞いて埋めるか、`references/diagram-patterns.md` の仮の色（黒・灰・強調色1つ）で作り、仮であることを伝える。

### 1. 題材の種類を見極める（ここを間違えると嘘の図になる）

| 種類 | 例 | やること |
|---|---|---|
| ① 一般の考え方・技術 | 「RLS って何」「MCP の仕組み」 | 知っている範囲で書く。**あいまいなら調べて裏をとってから**描く |
| ② 自社のシステム・コード | 「受注管理のデータの流れ」 | **必ず実物を読む**（ファイルを探して開く）。読んだファイルは7の欄に並べる |
| ③ 資料・議事録の構造 | 「この提案の論点の地図」 | その資料を読んで、論点とつながりを整理する |

> **②で推測の図を出してはいけない。** 実物と違う構成図は、読んだ人の頭に間違った地図を焼き付けるので、無いより悪い。
> 読めなかった所は図に描かず、「未確認」と書く。

### 2. 読み手を決める（最初に1問。指定があれば飛ばす）

| 段 | 読み手 | 書き方 |
|---|---|---|
| L1 自分・担当者用 | 頼んだ本人・エンジニア | 技術の言葉はそのまま。正確さ優先。実物のファイル名・関数名を添える |
| L2 お客様用 | 経営者・現場の担当者 | 仕事のたとえに置き換える。判断の軸と数字を前に出す。技術の名前には括弧で説明 |
| L3 初めての人用 | 新人・研修の受講者 | 前提ゼロ。やわらかい口調（あおらない・格好つけない） |

読み手が変われば、**同じ題材でも図の中身ごと変わる**。「言葉だけ易しくする」のでは L2・L3 にならない。

### 3. 図の型を選ぶ

6つの型から選ぶ。型と書き方の見本は **`references/diagram-patterns.md` を読む**（毎回ゼロから描かない）。

流れ図／層の図／関係図／比べる図／時の流れ／状態の移り変わり

### 4. 1枚のHTMLを組む

決まった雛形は使わない。中身に合わせて毎回組み立てる。並びは固定:

| # | かたまり | 中身 |
|---|---|---|
| 1 | **ひとことで言うと** | 1行のたとえ。ここだけ読んで7割分かる状態にする |
| 2 | **全体の図** | 大きな SVG 1枚。**このページの主役**。ここに一番時間を使う |
| 3 | **登場するもの** | 3〜6個の役割。上に罫線のあるカードで並べる。7個以上なら分けることを考える |
| 4 | **流れ** | 番号付きの手順。3〜5段がちょうどよい |
| 5 | **つまずきやすい所** | よくある誤解・実際にはまった落とし穴 |
| 6 | **言葉の説明** | 専門の言葉ごとの短い説明（初めて出た言葉は必ず説明する） |
| 7 | **実物との対応** | ②の時だけ。読んだファイルの場所・関数名を `<code>` で並べる |

文字の量の目安: **1〜5 の説明文を合わせて 800 字以内**（6・7 は参照用なので別枠）。
超えたら図で言えていない印。文章を足す前に図を描き直す。

見た目の決めごと（`DESIGN.md` に決まりがあればそちらが優先）:
- 絵文字を使わない。飾りのためのイラスト・写真を入れない
- 強調色は「その図で一番見てほしい1種類」だけ
- 専門の言葉は、初めて出た所で括弧で説明する（例: `MVP（最小限の機能で価値を試す試作版）`）
- 外部の CDN・JavaScript に頼らない。図はページの中に書いた SVG と CSS だけで作る

### 5. 確かめる（省略しない）

`references/verification.md` の手順で 1280px と 375px のスクショを撮り、**自分の目で見る**。
文字の検索や DOM の点検だけで合格にしない（日本語の折り返しの崩れ・SVG のはみ出しは、見ないと分からない）。

### 6. 置く

- 置き場所は `CLAUDE.md` の決まりに従う。その仕事の話をしているなら、その仕事の資料の場所（例: `projects/<名前>/docs/YYYY-MM-DD-<題名>-図解.html`）
- 置き場所に迷ったら、置く前に聞く
- お客様に渡す・外に公開する時は、本人の確認をとってから。お客様の名前・社内の情報が図に入っていないかも見る

## やらないこと

- **推測で構成図を描く**（②）— 実物を読む。読めなければ「未確認」と書く
- **文章のおまけに図を添える** — 図が主役。文章は図の補足
- **1枚に詰め込む** — 論点が2つ以上なら2枚に分ける
- **色だけで状態を表す** — 状態は「済／未」などの文字と、線の濃淡で示す
- **外部の CDN・JavaScript に頼る** — 図はページ内の SVG と CSS だけ
